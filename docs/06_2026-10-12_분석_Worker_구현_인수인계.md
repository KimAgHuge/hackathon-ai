# 6. 2026-10-12 분석 Worker 구현 인수인계

이 문서는 9월 23일 인수인계 이후 추가한 실제 분석 처리 경로를 설명한다.
이전 `05` 문서의 Worker·DB 메타데이터 수집 미구현 상태는 아래 내용으로 대체한다.
작업 시작 commit은 `4ffefc6`이다. 이후 변경은 수집기, Backend 분석 처리,
AI 프롬프트, Frontend, 문서로 나누어 관리한다. 공유 여부는 실제 Git 이력과
원격 브랜치를 확인하고, 실행 중인 서버의 반영 여부는 별도로 확인한다.

## 1. 이번 구현 범위

```text
화면에서 분석 시작
  → 저장된 Git 연결 재검증, commit SHA와 요구사항 version ID 기록
  → analysis_jobs PENDING
  → Backend Worker가 한 건 원자적으로 선점, RUNNING
  → 해당 Git commit의 일반 파일을 임시 디렉터리에 추출
  → 저장된 읽기 계정으로 DB 메타데이터 수집
  → 소스의 SQL·명시적 ORM 매핑과 실제 테이블 연결
  → 정제·크기 제한한 사실을 Mac FastAPI에 전달
  → Ollama 구조화 응답 검증
  → analysis_results 저장과 COMPLETED를 같은 transaction에서 반영
  → 프런트엔드에서 실제 상태/결과 표시
```

실패하면 단계명을 포함하는 안전한 메시지와 함께 `FAILED`로 기록한다.
Git/JDBC/HTTP 예외의 원문, 비밀번호와 토큰은 상태 메시지나 로그에 넣지 않는다.

이 구현은 **수집 범위 안의 DB 구조 및 소스 참조를 근거로 하는 분석**이다.
모든 함수 호출과 화면/API/Service 경로를 완전히 추적하는 호출 그래프는 아니다.
동적 SQL, 암묵적 ORM 이름, 컬럼별 사용 위치와 실행 시 검색 스키마에는 한계가 있다.
확정하지 못한 연결과 입력 축약 여부를 결과에 명시한다.

## 2. Backend 구성

| 파일/클래스 | 역할 |
|---|---|
| `AnalysisWorker` | 큐 처리, 단계별 상태, 수집·AI 호출·저장 연결 |
| `AnalysisJobRepository` | SKIP LOCKED 작업 선점, 진행률, 실패·고착 작업 처리 |
| `GitRepositoryConnectionService` | 기존 인증/호스트 정책 재사용, 저장된 commit 추출 |
| `DatabaseMetadataCollector` | 읽기 전용 연결과 테이블/컬럼/PK/FK/index 수집 |
| `SourceEvidenceCollector` | 실행하지 않는 소스 검사, 기술 및 DB 참조 근거 |
| `AnalysisPromptBuilder` | 모델 입력 크기 제한, 민감 키 차단, 수집 범위 기록 |
| `AiAnalysisClient` | 내부 API 키 인증, 응답 검증, 전체 요청 제한시간과 크기 제한 |
| `AnalysisResultRepository` | 원본 AI 결과·입력 근거와 완료 상태의 원자적 저장 |
| `AnalysisResultService/Controller` | 프로젝트 접근 권한을 확인하는 결과 조회 |

기존 `analysis_jobs`, `analysis_results` 구조를 사용하므로 **새 migration은 없다.**
기존 `001`~`007` 적용은 필요하다.

### 작업 및 결과 조회

```text
POST /api/projects/{projectId}/analysis-jobs
GET  /api/analysis-jobs/{jobId}
GET  /api/analysis-jobs/{jobId}/result
```

작업 조회에는 기존 필드 외에 `errorMessage`, `startedAt`, `completedAt`이 추가됐다.
결과 조회는 `ANALYSIS_READ`와 해당 프로젝트 접근 권한을 검사한다.
작업이 완료되지 않았으면 409, 접근 가능한 작업의 결과가 없으면 404를 반환한다.

결과 형태:

```json
{
  "jobId": "UUID",
  "projectId": "UUID",
  "summary": "한국어 분석 요약",
  "riskLevel": "UNKNOWN",
  "riskScore": 0,
  "result": {
    "summary": "한국어 분석 요약",
    "frameworks": [],
    "riskLevel": "UNKNOWN",
    "riskScore": 0,
    "impactAreas": [],
    "evidences": [],
    "recommendations": []
  },
  "facts": {
    "sourceSummary": {},
    "databaseSummary": {},
    "relations": []
  },
  "createdAt": "ISO-8601"
}
```

`original_result`에는 AI 응답을, `inference_metadata.facts`에는 **실제로 모델에
보낸 입력 사실**을 저장한다. 소스 원문과 접속정보는 넣지 않는다.

### 변경 요구사항을 지정하는 경우

기존 생성 API에 `requirementVersionId`를 전달하면 해당 프로젝트 소속인지 다시
검사하고 버전의 제목·정제 내용·인수 조건을 `sourceSummary.changeRequirement`에
포함한다. 값이 없으면 일반 구조 분석(`PROJECT_STRUCTURE_SCAN`)이다.

```json
{"requirementVersionId": "이미 생성한 요구사항 버전 UUID"}
```

프로젝트 등록 화면은 현재 요구사항 선택 없이 전체 구조 분석을 요청한다.
실제 API 모드의 변경요청 관리 화면에서는 Git 프로젝트의 요구사항을 조회·생성하고
현재 버전을 선택해 `requirementVersionId`를 포함한 분석을 요청할 수 있다.
기존 과거 버전 선택·수정 UI와 실제 환경에서의 변경 영향 분석 검증은 남아 있다.
새로운 요구사항 없이 특정 변경의 영향을 분석한 것처럼 표시하지 않는다.

## 3. 수집 범위와 한계

### Git

- 기존 저장소 호스트 allowlist, HTTPS/SSH 인증과 SSH host 검증을 사용한다.
- 프로젝트의 URL/브랜치가 대기 시점과 달라졌으면 실패한다.
- 해당 브랜치의 최근 100개 commit 범위를 가져온다. 기록된 commit을 찾을 수
  없으면 다른 commit으로 대체하지 않고 실패한다.
- bare 저장소의 Git 객체를 직접 읽으므로 checkout hook, smudge filter, LFS,
  submodule 및 프로젝트 script를 실행하지 않는다.
- symlink/gitlink, 알려진 바이너리/생성물/민감 파일은 추출하지 않는다.
  나머지 일반 파일 최대 10,000개, 단일 파일 2MiB, 총 64MiB 한도를 넘으면 실패한다.
- 수신 pack은 합계 128MiB, 객체 수 100,000개, 개별 객체 16MiB로 제한하며,
  임시 clone 디스크 사용도 256MiB를 기준으로 확인한다. 따라서 제외 대상 asset이라도
  Git 수신 단계의 한도를 넘으면 저장소 분석은 실패할 수 있다.
- HTTPS와 SSH에 동일한 pack parser 제한을 적용한다. 현재 고정한 JGit 버전의
  `FileRepository` inserter hook을 사용하므로 JGit 업그레이드 시 fetch 테스트를 재실행한다.
- 원격 전송은 최대 180초 transport timeout 및 약 3분 progress 취소 제한을 적용한다.
- 임시 저장소는 성공·실패 모두 정리하며, 모델을 기다리는 동안 보존하지 않는다.

### DB

- 저장된 주 연결의 비밀번호를 Backend에서만 복호화한다.
- PostgreSQL은 TLS와 JDBC read-only 설정에 더해 서버의
  `transaction_read_only=on`을 확인한다.
- Oracle은 실제 read-only transaction을 시작한다.
- 선택한 schema의 table/view, column 이름·타입·null 허용 여부, PK, FK,
  index만 JDBC metadata로 읽는다. 실제 업무 행은 조회하지 않는다.
- 최대 100개 table/view, 테이블당 100개 column, 키/index row 각 200개,
  수집 약 30초 한도 및 네트워크 timeout을 적용한다.
- 수집 한도로 생략하면 `truncated`와 `warnings`를 기록한다. 빈 schema는
  잘못된 이름/조회 권한 가능성을 경고한다.
- FK는 다른 schema 이름을 가리킬 수 있으나 다른 schema 전체를 수집하지 않는다.

### 소스

- Backend에서 실행되는 Java 수집기로 manifest 및 UTF-8 소스를 검사한다.
  Backend PC에 Python을 추가로 설치할 필요는 없다.
- JS/JVM/Python/Go/Rust/PHP/.NET/Dart 등 기술 선언과 파일 언어를 탐지한다.
- SQL 문자열, SQL 파일, MyBatis XML, 명시적 JPA/TypeORM/SQLAlchemy/Django/Prisma
  테이블 매핑을 실제 DB 객체와 대조한다.
- 근거에는 파일 경로·줄 번호·연결 종류·신뢰도만 포함한다. 코드 원문이나
  문자열에 포함된 실제 데이터/비밀번호는 전송하지 않는다.
- schema가 생략되거나 여러 객체에 대응하면 `tentative`/`ambiguous`로 표시한다.
- `.env`, 로컬 설정, key, 생성물, 바이너리와 symlink를 제외한다.
- 최대 3,000 파일, 파일당 256KiB, 총 16MiB, 깊이 25 등 한도를 적용한다.
- 기존 Python 기술 탐지기는 독립 CLI로 유지된다. 두 탐지기의 기술 규칙을
  공통 카탈로그로 통합하는 것은 향후 개선사항이다.

### AI 입력

- 모델에 보낼 JSON은 기본 최대 90,000자이다.
  Backend 환경변수 `DOENAAI_ANALYSIS_MAX_PROMPT_CHARS`로 조정할 수 있다.
- 참조된 테이블을 우선하고 최대 40개 테이블, 200개 관계, 150개 구성요소를
  시작점으로 크기를 줄인다. framework 근거는 기술당 3개까지만 전달한다.
- `sourceSummary.promptCoverage`에 수집 수/전송 수/생략 여부를 기록한다.
- 결과 화면에서 실제 전송한 범위의 개수와 생략 경고를 보여준다.
- 계정·토큰·비밀번호 필드는 입력 계약에서 거부한다. 요구사항에도 비밀번호나
  접속정보를 작성하지 않는다.

기존 45,000자 설정으로 완료된 분석에는 테이블 26/26개, 소스-테이블 참조 관계
25/61개가 전달된 것으로 표시됐다. 이 저장된 결과는 자동으로 바뀌지 않는다.
기본 한도를 90,000자로 올리고, 같은 규모의 재현 테스트에서 26개 테이블과
61개 관계 모두 입력에 포함되는 것을 확인했다. 이는 모델의 토큰 한도와
별개인 애플리케이션의 JSON 문자 수 제한이다. 실제 프로젝트의 입력 구성에
따라 일부가 여전히 생략될 수 있으므로 새 분석의 수집/전달 수를 다시 확인한다.
입력이 길어지면 응답 시간과 메모리 사용량도 증가할 수 있다.

## 4. 프런트엔드

`AnalysisProgressView.vue`는 고정 개수와 로그 대신 실제 작업 및 결과를 표시한다.

- 완료된 요청 이후 2.5초 간격으로 조회하며 중복 polling을 만들지 않는다.
- 화면 이동 시 요청과 예약된 polling을 취소한다.
- `COMPLETED`, `FAILED`, `CANCELLED`에서 자동 조회를 종료한다.
- 완료 시 결과 API의 요약·위험도·근거·권장사항·DB/소스 수집 수를 표시한다.
- 결과 조회만 실패하면 수동으로 다시 불러올 수 있다.
- Mock 모드에는 실제 분석이 아닌 데모라는 표시를 한다.
- 기존 통합 구조/영향도 전용 화면은 아직 별도 Mock 중심이며, 이번 결과 화면에서
  그 화면을 실제 분석 결과처럼 연결하지 않는다.
- 변경요청 관리의 실제 API 모드에서는 프로젝트별 요구사항 등록·조회와 현재 버전
  영향 분석을 지원한다. 프로젝트 등록 화면의 구조 분석 경로는 그대로 유지한다.

Backend:

```bash
cd backend

```

IntelliJ로 실행 중이면 중지 후 다시 실행한다. 저장된 기존 암호화 키를 유지해야
기존 Git/DB 인증정보를 읽을 수 있다. FastAPI 내부 API 키도 양쪽이 같아야 한다.

| 환경변수 | 기본값/의미 |
|---|---|
| `DOENAAI_AI_BASE_URL` | `http://localhost:8000`; 다른 PC의 Backend에서는 Mac 주소 |
| `DOENAAI_AI_INTERNAL_API_KEY` | 기존 FastAPI와 동일한 키 |
| `DOENAAI_AI_TIMEOUT_SECONDS` | 660초; FastAPI의 기본 최대 두 번 추론을 고려 |
| `DOENAAI_ANALYSIS_WORKER_ENABLED` | `true`; `false`이면 생성/조회만 하고 처리 중지 |
| `DOENAAI_ANALYSIS_MAX_PROMPT_CHARS` | `90000`; 모델 입력 JSON의 문자 수 상한 |
| `DOENAAI_ANALYSIS_POLL_DELAY_MS` | 2500 |
| `DOENAAI_ANALYSIS_STALE_TIMEOUT_SECONDS` | 1800; 중단되어 남은 RUNNING 작업 실패 처리 |

고착 판정의 실제 하한은 AI timeout + 600초이다. 다음 poll에서 처리하며,
실패한 작업을 자동 재시도하지 않는다. 재분석은 새 작업으로 요청한다.
모델 부하를 제한하려면 **Worker를 켜는 Backend 인스턴스는 하나**로 운영한다.
큐의 선점은 여러 작업자 간 중복을 방지하지만, 모델 호출 동시성 제한은 프로세스별이다.

Frontend:

```bash
cd frontend
npm run dev
```

실제 API 모드(`VITE_USE_MOCK=false`)에서 기존 저장소/DB 연결로 분석을 시작한다.
Backend를 재시작하면 남아 있던 `PROJECT_SCAN/PENDING` 작업도 순서대로 처리한다.

## 6. 검증 및 이어서 확인할 내용

자동 테스트는 운영 Supabase 자격증명을 사용하지 않는다.

```bash
cd backend

# 별도 일회용 로컬 PostgreSQL에서만 실행하는 repository 통합 테스트
DOENAAI_TEST_POSTGRES_URL=jdbc:postgresql://127.0.0.1:<테스트포트>/doenaai_worker_test \

node --test tests/*.test.js
npm run build

cd ../ai-server
.venv/bin/python -m pytest -q
```

검증 범위: 읽기 전용 실패 차단, DB metadata 필드·범위 제한, 소스/ORM 근거와
민감 파일 제외, commit 고정 추출, Worker 성공/실패 및 정리, 입력 크기 제한,
결과 접근 제어, HTTP 인증/응답·본문 정지 timeout, UI polling.
PostgreSQL 통합 테스트는 별도 테스트 DB에서 실제 선점 경쟁과 결과 저장 transaction을 검증한다.

2026-10-12 확인 결과: Backend build/test 성공, 일회용 PostgreSQL 통합 테스트
7개 성공, 프런트엔드 polling 테스트 11개 및 production build 성공,
AI 분석/추론 서버 테스트 25개 성공. 현재 Mac의 `/health`와 Ollama `/api/tags` 응답도 확인했다.

위 자동 검증과 별개로, 2026-10-12 오후 실제 등록 프로젝트의 구조 분석이
`COMPLETED`로 끝났고 결과 화면에 테이블 26/26개와 관계 81/81개가 표시됐다.
변경요청 관리 화면에서 현재 요구사항 버전을 지정하는 코드도 연결했으며,
프런트엔드 Node 테스트 14개와 production build가 통과했다. 다만 요구사항을
지정한 실제 분석과 결과의 schema/table/file 근거 정확도는 계속 검증해야 한다.

다음 개선 우선순위:

1. 완료된 구조 분석의 schema/table/file 근거를 실제 코드·DB와 대조
2. 실제 요구사항 하나의 현재 버전으로 변경 영향 분석을 실행·검토
3. API/Service/화면 호출 관계와 컬럼별 사용 근거 확장
4. 모델 입력 검색·분할 분석으로 대규모 저장소와 schema 범위 확대

기존 `.env`, `application-local.yml`, 실제 API/DB/Git 키는 변경하지 않는다.

## 7. Backend → FastAPI HTTP 업그레이드 오류 수정

2026-10-12 실제 연결에서 내부 API 키가 정상이어도 Uvicorn에
`Unsupported upgrade request`, `Invalid HTTP request received` 경고와
즉시 발생하는 422 오류가 기록되는 문제를 확인했다.

Java HttpClient의 기본 HTTP/2 업그레이드 시도가 현재 Uvicorn의 요청 본문
처리와 충돌했다. 같은 진단용 JSON으로 비교하면 기본 설정은 HTTP 400으로
실패했고, HTTP/1.1을 명시한 요청은 HTTP 200으로 분석 결과를 반환했다.
이 문제는 모델 추론 시간이나 DB 읽기 속도와 별개다.

- `AiAnalysisClient`에서 `HttpClient.Version.HTTP_1_1`을 명시한다.
- 회귀 테스트는 실제 수신 요청의 프로토콜, `Upgrade`/`HTTP2-Settings` 헤더
  부재, 인증 헤더와 JSON 본문 전달을 검사한다.
- 적용하려면 **Backend를 완전히 중지 후 다시 실행**하고 새 분석 작업을 시작한다.
  이미 실패한 작업의 상태 조회는 재실행이 아니다.
- 이 수정 때문에 내부 API 키를 다시 만들거나 모델을 재설치할 필요는 없다.
- 작은 진단 요청 성공과 실제 등록 프로젝트의 전체 분석 완료 검증은 구분한다.

수정 전 회귀 테스트에서 `Upgrade: h2c` 전송으로 실패하는 것을 확인했고,
HTTP/1.1 고정 후 `bash ./gradlew build`가 성공했다. Backend 테스트 94개가
통과했으며, 별도 PostgreSQL이 필요한 선택적 통합 테스트 7개는 이번 실행에서
건너뛰었다. 실행 중인 Backend 프로세스 재시작과 실제 프로젝트 재분석은 별도다.
