# doenaai 데이터베이스 구조 설계서

## 1. 문서 목적

이 문서는 현재까지 설계한 `doenaai`의 Supabase PostgreSQL 테이블 구조, 테이블 간 관계, 각 테이블의 책임, 그리고 이러한 구조로 설계한 이유를 정리한다.

현재 시스템은 다음 구성을 전제로 한다.

```text
Client Browser
    ↓
Vue 3
    ↓
Spring Boot
    ├─ Supabase Auth / PostgreSQL
    ├─ Mac Studio AI Server (FastAPI)
    └─ M4 Max Training Worker
```

핵심 원칙은 다음과 같다.

- 사용자 인증은 Supabase Auth가 담당한다.
- 업무 권한과 비즈니스 로직은 Spring Boot가 담당한다.
- 브라우저가 업무 테이블을 직접 조회·수정하지 않는다.
- Mac Studio는 AI 추론 엔진 역할에 집중한다.
- M4 Max는 학습 Worker 역할에 집중한다.
- AI 원본 결과와 사람이 수정한 결과를 모두 보존한다.
- 모델 학습, 평가, 버전 관리, 배포 이력을 DB에서 추적할 수 있게 한다.
- 향후 RAG를 추가할 수 있도록 pgvector와 Embedding/Reranker 모델 구조를 고려한다.

# 4. 사용자 / 권한 구조

## 4.1 `auth.users`

`auth.users`는 직접 만든 테이블이 아니라 Supabase Auth가 관리하는 시스템 테이블이다.

주요 책임:

- 이메일/비밀번호 인증
- 사용자 UUID 생성
- JWT 발급
- 이메일 확인 상태 관리
- 인증 메타데이터 관리

### 이렇게 만든 이유

비밀번호 저장, 해싱, 토큰 발급을 애플리케이션에서 직접 구현하지 않기 위해서다.

```text
Vue
 ↓ 로그인
Supabase Auth
 ↓ JWT
Vue
 ↓ Bearer Token
Spring Boot
```

Spring Boot는 비밀번호를 알 필요가 없고 JWT만 검증하면 된다.

---

## 4.2 `profiles`

Supabase Auth 사용자와 1:1로 연결되는 업무용 사용자 프로필이다.

주요 컬럼:

| 컬럼 | 설명 |
|---|---|
| `id` | `auth.users.id`와 동일한 UUID |
| `display_name` | 화면 표시 이름 |
| `department` | 부서 |
| `job_title` | 직급 |
| `status` | `ACTIVE`, `INACTIVE`, `BLOCKED` |
| `last_login_at` | 마지막 로그인 시간 |
| `created_at` | 생성 시간 |
| `updated_at` | 수정 시간 |

### 이렇게 만든 이유

인증 정보와 업무 정보를 분리하기 위해서다. `auth.users`는 인증에 집중하고, 애플리케이션에서 필요한 이름, 부서, 상태 등은 `profiles`에서 관리한다.

또한 사용자를 삭제하지 않고도 `INACTIVE`, `BLOCKED` 상태로 접근을 제한할 수 있다.

---

## 4.3 `roles`

시스템 전역 역할을 관리한다.

기본 역할:

```text
ADMIN
ANALYST
VIEWER
```

### 이렇게 만든 이유

사용자별로 개별 권한을 직접 지정하면 관리가 복잡해지기 때문에 RBAC(Role-Based Access Control) 구조를 사용했다.

```text
사용자
 ↓
역할
 ↓
권한
```

---

## 4.4 `permissions`

실제 기능 단위의 권한을 관리한다.

예:

```text
PROJECT_READ
PROJECT_CREATE
PROJECT_UPDATE
CHANGE_REQUEST_READ
CHANGE_REQUEST_CREATE
CHANGE_REQUEST_UPDATE
ANALYSIS_READ
ANALYSIS_EXECUTE
ANALYSIS_APPROVE
MODEL_READ
MODEL_TRAIN
MODEL_EVALUATE
MODEL_DEPLOY
MODEL_ROLLBACK
USER_MANAGE
```

### 이렇게 만든 이유

`ADMIN`, `ANALYST` 같은 역할명에 기능을 하드코딩하지 않고 세부 권한으로 분리하면 향후 새로운 역할을 쉽게 추가할 수 있다.

예를 들어 `REVIEWER`, `MODEL_MANAGER` 같은 역할을 새로 만들더라도 기존 소스 구조를 크게 바꿀 필요 없이 권한 조합만 변경하면 된다.

---

## 4.5 `user_roles`

사용자와 역할의 N:M 관계를 관리한다.

```text
auth.users
     │
     ▼
user_roles
     │
     ▼
roles
```

복합 PK:

```text
(user_id, role_id)
```

한 사용자가 여러 역할을 가질 수 있도록 확장성을 확보했다.

---

## 4.6 `role_permissions`

역할과 권한의 N:M 관계를 관리한다.

```text
roles
   │
   ▼
role_permissions
   │
   ▼
permissions
```

Spring Boot에서는 다음과 같은 방식으로 사용자의 최종 권한 목록을 가져올 수 있다.

```sql
select distinct p.code
from public.user_roles ur
join public.role_permissions rp
    on rp.role_id = ur.role_id
join public.permissions p
    on p.id = rp.permission_id
where ur.user_id = :userId;
```

# 5. 프로젝트 구조

## 5.1 `projects`

분석 대상 프로젝트를 관리한다.

주요 컬럼:

| 컬럼 | 설명 |
|---|---|
| `id` | 프로젝트 UUID |
| `name` | 프로젝트명 |
| `description` | 설명 |
| `repository_url` | Git Repository 주소 |
| `default_branch` | 기본 브랜치 |
| `status` | `ACTIVE`, `INACTIVE`, `ARCHIVED` |
| `created_by` | 생성 사용자 |
| `created_at` | 생성 시간 |
| `updated_at` | 수정 시간 |

### UUID를 사용한 이유

주요 업무 Entity의 PK를 UUID로 통일했다.

```text
auth.users       UUID
projects         UUID
change_requests  UUID
analysis_jobs    UUID
analysis_results UUID
ai_models        UUID
model_versions   UUID
```

Spring Boot에서도 `UUID` 타입으로 일관되게 처리할 수 있고 분산 환경에서도 ID 생성 충돌 가능성이 낮다.

---

## 5.2 `project_members`

프로젝트별 사용자를 관리한다.

프로젝트 내부 역할:

```text
OWNER
MANAGER
ANALYST
VIEWER
```

복합 PK:

```text
(project_id, user_id)
```

### 전역 역할과 분리한 이유

`roles.ADMIN`과 `project_members.OWNER`는 의미가 다르다.

```text
roles.ADMIN
→ 시스템 전체 관리자

project_members.OWNER
→ 특정 프로젝트의 소유자
```

한 사용자가 시스템 전체에서는 `ANALYST`이지만 특정 프로젝트에서는 `OWNER`일 수도 있기 때문에 별도로 관리한다.

# 6. 변경요청 구조

## 6.1 `change_requests`

AI에게 분석시킬 변경사항 자체를 저장한다.

주요 컬럼:

| 컬럼 | 설명 |
|---|---|
| `id` | 변경요청 UUID |
| `project_id` | 대상 프로젝트 |
| `title` | 변경요청 제목 |
| `description` | 변경 내용 |
| `source_type` | 변경 출처 |
| `source_ref` | Commit SHA, PR 번호 등 |
| `base_ref` | 비교 기준 브랜치/커밋 |
| `target_ref` | 변경 대상 브랜치/커밋 |
| `status` | 변경요청 상태 |
| `metadata` | Git 등 추가 정보 |
| `created_by` | 등록 사용자 |

`source_type`:

```text
MANUAL
GIT_COMMIT
PULL_REQUEST
OTHER
```

### 분석 작업과 분리한 이유

하나의 변경요청은 여러 번 분석될 수 있다.

```text
Change Request 1
    ├─ Analysis Job 1
    ├─ Analysis Job 2
    └─ Analysis Job 3
```

재분석, 다른 모델을 이용한 분석, 옵션 변경 후 분석 등을 지원하기 위해 변경요청과 분석 실행을 분리했다.

# 7. AI 분석 구조

## 7.1 `analysis_jobs`

실제 AI 분석 실행 단위를 관리한다.

주요 컬럼:

| 컬럼 | 설명 |
|---|---|
| `project_id` | 프로젝트 |
| `change_request_id` | 변경요청 |
| `requested_by` | 실행 요청 사용자 |
| `analysis_type` | 분석 종류 |
| `status` | 실행 상태 |
| `source_progress` | 소스 분석 진행률 |
| `database_progress` | DB 분석 진행률 |
| `relation_progress` | 관계 분석 진행률 |
| `analysis_options` | 분석 옵션 JSON |
| `input_snapshot` | 분석 당시 입력 Snapshot |
| `model_version_id` | 실제 사용 모델 버전 |
| `error_message` | 실패 메시지 |
| `started_at` | 시작 시간 |
| `completed_at` | 완료 시간 |

상태:

```text
PENDING
RUNNING
COMPLETED
FAILED
CANCELLED
```

### `input_snapshot`을 둔 이유

Git과 변경요청 내용은 이후 수정될 수 있으므로 분석 당시 입력값을 보존해야 나중에 "이 결과가 정확히 어떤 입력으로 생성되었는가"를 확인할 수 있다.

---

## 7.2 `analysis_results`

AI 결과와 사람이 수정한 최종 결과를 보관한다.

주요 컬럼:

| 컬럼 | 설명 |
|---|---|
| `analysis_job_id` | 분석 작업 |
| `original_result` | AI 원본 결과 JSON |
| `corrected_result` | 사용자 수정 결과 JSON |
| `risk_level` | LOW / MEDIUM / HIGH / CRITICAL |
| `summary` | 분석 요약 |
| `approved` | 승인 여부 |
| `approved_by` | 승인 사용자 |
| `approved_at` | 승인 시간 |
| `review_note` | 검토 메모 |
| `inference_metadata` | 추론 시간, 토큰량 등 |

### 원본과 수정 결과를 분리한 이유

`doenaai`의 핵심 목표 중 하나는 AI 결과를 사람이 검토하고 그 차이를 학습 데이터로 축적하는 것이다.

```text
AI 결과
original_result
      ↓
사람 검토 및 수정
      ↓
corrected_result
      ↓
승인
      ↓
학습 데이터로 활용
```

AI 원본을 덮어쓰지 않으므로 모델의 실제 성능도 추적할 수 있다.

# 8. AI 모델 관리 구조

## 8.1 `ai_models`

논리적인 AI 모델 단위를 관리한다.

예:

```text
doenaai-code-analyzer
doenaai-embedding
doenaai-reranker
```

`model_type`:

```text
LLM
EMBEDDING
RERANKER
```

### 모델과 버전을 분리한 이유

하나의 논리 모델에 여러 실제 버전이 존재할 수 있기 때문이다.

```text
doenaai-code-analyzer
├─ 1.0.0
├─ 1.1.0-LoRA
└─ 1.2.0-LoRA
```

`ai_models`는 모델 자체의 개념을 관리하고, 실제 파일과 학습 산출물은 `model_versions`에서 관리한다.

---

## 8.2 `model_versions`

실제로 사용할 수 있는 모델 산출물을 관리한다.

주요 컬럼:

| 컬럼 | 설명 |
|---|---|
| `model_id` | 논리 모델 |
| `training_job_id` | 해당 버전을 만든 학습 작업 |
| `version` | 모델 버전 |
| `artifact_type` | BASE / LORA / MERGED / EXTERNAL |
| `base_model_ref` | Base Model |
| `artifact_uri` | 전체 모델 위치 |
| `adapter_uri` | LoRA Adapter 위치 |
| `checksum` | 파일 무결성 정보 |
| `metadata` | 추가 정보 |

### 이렇게 만든 이유

학습을 수행할 때마다 새로운 LoRA Adapter나 모델 산출물이 생성된다. 이를 파일명만으로 관리하지 않고 DB에서 버전과 생성 이력을 추적할 수 있게 하기 위해서다.

---

# 9. 학습 구조

## 9.1 `training_datasets`

학습 데이터셋의 메타데이터를 관리한다.

주요 컬럼:

| 컬럼 | 설명 |
|---|---|
| `name` | 데이터셋명 |
| `source_type` | 데이터 생성 출처 |
| `dataset_format` | JSONL / JSON / CSV / PARQUET |
| `storage_provider` | LOCAL / SUPABASE_STORAGE / S3 |
| `storage_uri` | 실제 데이터 위치 |
| `example_count` | 예제 수 |
| `status` | PREPARING / READY / ARCHIVED / FAILED |
| `metadata` | 추가 정보 |

### 파일 자체를 DB에 넣지 않는 이유

학습 데이터가 커질 수 있으므로 PostgreSQL에는 메타데이터와 위치만 저장하고 실제 데이터는 파일 시스템이나 Storage에 보관하도록 설계했다.

---

## 9.2 `training_jobs`

M4 Max Training Worker가 처리할 학습 작업이다.

주요 컬럼:

| 컬럼 | 설명 |
|---|---|
| `model_id` | 학습 대상 모델 |
| `dataset_id` | 사용할 데이터셋 |
| `status` | 작업 상태 |
| `progress` | 진행률 |
| `worker_name` | 작업을 가져간 서버 |
| `base_model_ref` | Base Model |
| `hyper_parameters` | 학습 파라미터 JSON |
| `output_uri` | 학습 결과 위치 |
| `log_uri` | 로그 위치 |
| `heartbeat_at` | Worker 생존 시간 |

상태:

```text
PENDING
CLAIMED
RUNNING
COMPLETED
FAILED
CANCELLED
```

### `CLAIMED` 상태를 둔 이유

향후 Training Worker가 여러 대가 되더라도 하나의 작업을 두 서버가 동시에 가져가지 않도록 확장할 수 있게 하기 위해서다.

# 10. 모델 평가 구조

## 10.1 `model_evaluations`

학습된 모델을 실제 AI 서버에 적용하기 전에 평가 결과를 저장한다.

주요 컬럼:

| 컬럼 | 설명 |
|---|---|
| `model_version_id` | 평가 대상 버전 |
| `dataset_id` | 평가 데이터셋 |
| `evaluation_type` | AUTOMATIC / MANUAL / BENCHMARK |
| `status` | PENDING / RUNNING / PASSED / FAILED |
| `metrics` | 상세 지표 JSON |
| `overall_score` | 종합 점수 |
| `notes` | 평가 메모 |

### 이렇게 만든 이유

학습이 성공했다고 해서 반드시 기존 모델보다 성능이 좋은 것은 아니므로 다음 흐름을 지원하기 위해서다.

```text
Training 완료
   ↓
Model Version 생성
   ↓
Evaluation
   ↓
PASSED
   ↓
Deployment
```

# 11. 모델 배포 구조

## 11.1 `model_deployments`

Mac Studio AI 서버에서 현재 실제로 어떤 모델을 사용하고 있는지 기록한다.

주요 컬럼:

| 컬럼 | 설명 |
|---|---|
| `model_version_id` | 실제 모델 버전 |
| `server_name` | 모델을 사용하는 서버 |
| `deployment_role` | ANALYSIS / EMBEDDING / RERANKING |
| `status` | ACTIVE / INACTIVE / FAILED |
| `endpoint_url` | 내부 Endpoint |
| `deployed_at` | 활성화 시간 |
| `undeployed_at` | 비활성화 시간 |

하나의 서버/역할에는 ACTIVE 모델이 하나만 존재하도록 Partial Unique Index를 둔다.

```text
mac-studio-ai
├─ ANALYSIS   → v1.2.0 ACTIVE
├─ EMBEDDING  → embedding-v1 ACTIVE
└─ RERANKING  → reranker-v1 ACTIVE
```

### 이렇게 만든 이유

모델 교체와 롤백을 단순 파일 복사로 처리하지 않고, 어떤 버전이 언제 어디에 활성화되었는지를 추적하기 위해서다.

# 12. 서버별 책임

## Vue

```text
Supabase Auth 로그인
Spring Boot API 호출
```

업무 테이블에는 직접 접근하지 않는다.

## Spring Boot

DB 접근의 중심이다.

```text
사용자/권한 조회
프로젝트 CRUD
변경요청 CRUD
분석 작업 생성
분석 결과 저장
모델 관리
학습 작업 관리
모델 배포 관리
```

## Mac Studio AI Server

FastAPI 기반 AI 추론 서버다.

```text
Spring Boot
     ↓ HTTP
Mac Studio FastAPI
     ↓
LLM 추론 / Embedding / 향후 Reranking
     ↓
Spring Boot
     ↓
Supabase
```

### DB 직접 접근을 최소화한 이유

AI 서버에 DB 비밀번호와 전체 업무 권한을 줄 필요가 없기 때문이다. AI 서버는 분석 엔진 역할에 집중하고 데이터 저장은 Spring Boot가 담당한다.

## M4 Max Training Server

```text
Training Job
    ↓
M4 Max Worker
    ↓
LoRA 학습
    ↓
Model Version
```

학습 작업을 가져가 처리하고 결과 모델을 생성한다.

# 13. RLS 및 브라우저 직접 접근 제한

업무 테이블은 RLS를 활성화하고 `anon`, `authenticated` 역할의 직접 테이블 권한을 제한하는 방향으로 설계했다.

```text
Browser
   X
Supabase 업무 테이블

Browser
   ↓
Spring Boot
   ↓
PostgreSQL
```

### 이렇게 만든 이유

권한 판단을 Vue, Supabase 정책, Spring Boot 여러 곳에 분산시키기보다 Spring Boot에 집중시키기 위해서다.

```text

analysis_jobs
analysis_results
ai_models
training_datasets

```

### 이렇게 만든 이유

애플리케이션에서 매번 `updated_at` 값을 직접 수정하지 않아도 DB가 자동으로 변경 시간을 기록하도록 하기 위해서다.

# 15. JSONB를 사용한 이유

다음과 같이 AI 관련 상세 정보는 JSONB를 적극 사용한다.

```text
change_requests.metadata
analysis_jobs.analysis_options
analysis_jobs.input_snapshot
analysis_results.original_result
analysis_results.corrected_result
analysis_results.inference_metadata
training_jobs.hyper_parameters
model_versions.metadata
model_evaluations.metrics
model_deployments.metadata
```

AI 출력 구조와 학습 파라미터는 개발 중 자주 변경될 가능성이 크다.

따라서:

```text
검색/필터링이 중요한 값
→ 일반 컬럼

구조가 자주 바뀌는 상세 데이터
→ JSONB
```

방식으로 설계했다.

예:

```text
risk_level
→ 일반 컬럼

전체 AI 응답
→ original_result JSONB
```

# 17. 향후 RAG 확장

현재 RAG 전용 테이블은 아직 만들지 않았다.

다만 다음 기반은 이미 준비했다.

```text
pgvector extension
ai_models.model_type = EMBEDDING
ai_models.model_type = RERANKER
model_deployments.deployment_role = EMBEDDING
model_deployments.deployment_role = RERANKING
```

향후 `004_documents_rag.sql`에서 다음 구조를 추가할 수 있다.

```text
projects
   │
   ▼
documents
   │
   ▼
document_chunks
   │
   ├─ content
   ├─ embedding
   └─ embedding_model_version_id
```

예상 관계:

```text
document_chunks
      │
      ├─ content
      └─ embedding
             │
             ▼
       model_versions
             │
             ▼
         ai_models
         EMBEDDING
```

### 지금 RAG 테이블을 만들지 않은 이유

Embedding 모델마다 벡터 차원이 다를 수 있기 때문이다.

```text
768
1024
1536
3072
...
```

실제 Embedding 모델이 확정되기 전에 `vector(n)`을 고정하면 나중에 Migration이 필요할 수 있으므로 현재는 pgvector와 모델 관리 구조만 준비했다.

# 21. 설계 요약

현재 DB 구조는 단순 CRUD용 테이블 모음이 아니라 다음 전체 Lifecycle을 고려했다.

```text
사용자 인증/권한
      ↓
프로젝트 관리
      ↓
변경요청
      ↓
AI 영향도 분석
      ↓
사람의 검토 및 수정
      ↓
승인 결과 축적
      ↓
학습 데이터 생성
      ↓
LoRA 학습
      ↓
모델 평가
      ↓
모델 버전 관리
      ↓
Mac Studio 배포
      ↓
향후 RAG 확장
```

핵심 설계 의도:

- 인증 정보와 업무 사용자 정보를 분리한다.
- 전역 역할과 프로젝트 내부 역할을 분리한다.
- 변경요청과 분석 작업을 분리해 재분석을 지원한다.
- AI 원본 결과와 사용자 수정 결과를 모두 보존한다.
- 승인된 결과를 향후 학습 데이터로 연결할 수 있게 한다.
- 학습 작업과 모델 버전의 생성 관계를 추적한다.
- 모델 버전과 실제 배포 상태를 분리한다.
- AI 서버와 Training 서버가 DB 구조에 과도하게 결합되지 않도록 한다.
- JSONB를 활용해 AI 출력 구조 변경에 유연하게 대응한다.
- 현재 RAG를 구현하지 않더라도 Embedding/Reranker/pgvector 확장 가능성을 확보한다.
