# doenaai 프로젝트 개요

기준일: 2026-10-21

`doenaai`는 고객의 변경 요구사항을 프로젝트 소스와 DB 구조에 연결해 영향 범위와
기술 위험을 설명하고, PM·PL의 작업량·일정·견적 판단을 돕는 서비스다.
정적 분석으로 수집한 근거를 AI가 해석하며, 최종 범위와 견적은 사람이 결정한다.

- 서버 구성과 처리 흐름: [시스템 아키텍처](02_시스템_아키텍처.md)
- 현재 구현 범위와 남은 검증: [현재 진행상황](03_현재_진행상황.md)
- 화면에서 모델 학습·등록·적용하기: [AI 모델 관리 사용 안내](18_AI_모델_관리_사용_안내.md)
- 설치와 실행: [저장소 안내](../README.md)

## 주요 사용자와 업무

| 사용자 | 주요 업무 |
|---|---|
| PM | 고객 요구사항 정리, 분석 결과 검토, 일정·비용 판단 |
| PL·개발자 | 소스·DB 근거 확인, 구현 범위·위험·테스트 검토 |
| 모델 운영자 | 승인 자료 관리, 모델 학습·검증·적용 |
| 관리자 | 사용자·권한·조직·연결 정책 관리 |

대표 흐름은 다음과 같다.

```text
프로젝트와 Git·DB 연결 등록
  → 요구사항 입력과 분석 요청
  → 소스·DB 구조 수집
  → AI의 영향 범위·위험·근거 제안
  → 사람의 수정·승인
  → 승인 자료로 모델 추가 학습
  → 새 모델 생성·검증·적용
```

분석은 등록한 프로젝트의 고정 커밋과 읽기 전용 DB 구조를 기준으로 한다.
프로젝트를 등록할 때마다 새 모델을 학습시키지 않는다. 학습은 사람이 승인한 자료로
별도 요청하며, 완료된 학습 결과도 사용자가 검증하고 적용해야 분석에 사용된다.

## 저장소와 기술 구성

| 경로 | 역할 | 주요 기술 |
|---|---|---|
| `frontend/` | 업무 화면과 상태 조회 | Vue 3, Vite, Pinia, Axios |
| `backend/` | 인증·권한, 연결 관리, 근거 수집, 작업·결과 저장 | Java 25, Spring Boot, JGit, JDBC |
| `ai-server/` | 분석 입력·응답 검증, 모델 호출과 등록 | Python, FastAPI, Pydantic |
| `training/` | 승인 자료 수신·검사, 학습, 완성 모델 생성 | Python, MLX-LM, LoRA, llama.cpp |
| `shared/` | 서비스 간 JSON 계약 | JSON Schema |
| `supabase/` | 인증과 업무 DB 스키마 | Supabase Auth, PostgreSQL, migration SQL |
| `docs/` | 제품·구조·현황·운영 안내 | Markdown |

정확한 패키지 버전과 설치 방법은 각 서비스의 의존성 파일과 README를 따른다.
DB 구조는 [Supabase migration](../supabase/README.md)으로 관리하며 Hibernate 자동 생성에 의존하지 않는다.

## 핵심 원칙

### 근거와 재현성

분석 입력에는 프로젝트, 요구사항 버전, Git 커밋, DB 구조와 수집 범위를 연결한다.
파일·줄 번호·테이블 등의 근거를 남기고, 잘리거나 수집하지 못한 범위는 경고로 표시한다.
AI가 제안한 위험 점수는 판단 보조값이다. 수집되지 않은 관계를 영향이 없는 것으로 해석하지 않는다.

현재 수집기는 기술 선언, 소스 참조와 명시적 DB 매핑을 찾는다. 동적 SQL,
모든 프레임워크의 호출 관계, 컬럼별 사용 위치를 완전히 추적하는 분석기로 보아서는 안 된다.

### 비동기 작업

분석·학습·모델 생성·등록 요청의 응답은 작업 접수 또는 현재 상태다.
화면은 작업 식별자로 진행 상황과 결과를 조회한다. 응답 지연이나 통신 중단 때는
기존 작업을 먼저 확인하고 같은 작업을 중복 실행하지 않는다.

### 사람의 검토와 모델 이력

AI 원본, 수정 결과와 승인 기록을 구분한다. 미승인 모델 출력과 도구 시험용 답변을
학습 정답으로 취급하지 않는다. 학습 자료는 분석을 생성한 모델의 기반 계열별로 나누고,
새 모델로 생성한 분석에는 실제 모델 식별값을 남긴다.

학습 손실 감소·어댑터 저장·JSON 응답 검증은 각각 다른 확인이다.
이 결과만으로 실제 업무 품질 개선을 확정하지 않으며 같은 입력·조건의 비교와 사람 검토를 유지한다.
Qwen은 초기 기본 모델이며 모델이 바뀌어도 이러한 기준은 동일하다.

### 데이터와 권한 경계

- 브라우저는 Supabase Auth로 로그인하고 업무 API는 백엔드를 거친다.
- 최종 권한과 조직·프로젝트 접근 범위는 백엔드에서 검사한다. 화면의 버튼 숨김은 권한 검사를 대신하지 않는다.
- 플랫폼 DB 계정과 분석 대상 DB의 읽기 계정은 역할이 다르다. 연결정보 저장으로 대상 DB 계정을 생성하지 않는다.
- Git·DB 비밀번호와 토큰은 백엔드에서 암호화하고 모델 입력·응답·로그·문서·Git에 넣지 않는다.
- 브라우저에는 공개 클라이언트 키만 사용하며 Supabase 비밀 키나 내부 서버 키를 전달하지 않는다.
- 고객 요구사항의 자유 입력에도 개인정보와 접속 비밀을 적지 않는다.
- 모델 파일, 학습 자료, 어댑터와 전체 실행 보고서는 Git에서 제외한다.

견적·고객 공개 등 최종 제품 목표의 구현 여부는 [현재 진행상황](03_현재_진행상황.md)에서 확인한다.
