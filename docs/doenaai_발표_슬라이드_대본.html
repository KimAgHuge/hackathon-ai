※ 실제 업무 과정을 설명하기 위한 예시 화면입니다.

현재 저희는 소상공인24 경영안전바우처팀에서 유지보수 업무를 하고 있습니다. 일을 하다보면 고객의 요청은 매일 들어옵니다. 이 요청 중에서 간단한 요청도 있지만 기능에 대한 개선이나 추가 요청이 들어오는 경우도 있습니다. 이 때 고객의 요청은 한 줄로 들어옵니다.

고객 : “책임님~ 심의 단계에서 검증하는 기능을 추가할 수 있을까요?”

담당자 : “요청하신 내용 확인해 보겠습니다. 기존 로직에 어떤 영향이 있을지 검토가 필요해서, 확인 후 다시 말씀드리겠습니다.”

고객에게는 간단한 질문이지만, 저희가 답변하기 위해서는 소스 코드를 분석하고, 수정이 필요한 부분과 다른 기능에 미치는 영향, 작업량과 일정까지 확인해야 합니다. 이처럼 간단한 요청 하나에도 답변하기까지 여러 단계의 분석 과정이 필요합니다.

PROBLEM 2
기능 개선 요청 이후, 실제 업무 과정

개발보다 오래 걸리는 건,
분석입니다.

1영향도 분석 및 작업량 산정30%
2기존 시스템 분석25%
3기능 구현20%
4테스트 및 검증15%
5요구사항 분석10%
구현하는 시간보다 “분석하는 시간”이 더 깁니다.
그동안 고객은 답을 기다립니다.
65%분석 업무가
차지하는 비중
※ 경영안전바우처 유지보수팀의 업무 경험을 바탕으로 산정한 주관적 추정치입니다.

실제 저희 유지보수팀의 경험을 바탕으로, 기능 개선이나 추가 요청이 들어왔을 때 업무 비중을 주관적으로 시각화해 봤습니다. 보시는 것처럼 기존 시스템 분석에 25%, 영향도 분석 및 작업량 산정에 30%, 요구사항 분석에 10%로,

분석 업무가 전체의 65%를 차지합니다. 즉, 실제 기능을 구현하는 시간보다 분석에 더 많은 시간이 소요되는 것입니다.

그리고 이 분석이 끝나고 답을 내리기 전까지, 고객은 계속 답변을 기다립니다. 저희는 바로 이 분석 시간을 줄이는 것에서 출발했습니다.

WHY DOENAAI
기존 방식의 한계

문제는 시간만이 아니었습니다.

분석 결과를 판단하고, 고객에게 전달하는 과정에도 한계가 있었습니다.

한계 1

담당자에 따른 분석 편차

경험과 지식에 따라
분석 결과가 달라질 수 있습니다

한계 2

고객과 개발자 간의 소통

기술적인 분석 결과를
고객이 이해하기 쉽게 설명해야 합니다

한계 3

분석 근거의 확인과 공유

결과를 검토하고
설명할 수 있는 근거가 필요합니다

“이 기능, 되나요?”

고객의 질문에서 출발해, 실제 시스템을 분석하고 근거 있는 답변을 제시하는 플랫폼입니다.

분석 시간 말고도 한계가 있었습니다. 분석 결과를 판단하고, 고객에게 전달하는 과정에서도 어려움이 있었는데요.

첫 번째로 담당자의 경험과 지식에 따라 분석 결과에 차이가 생길 수 있습니다.

두 번째는 기술적인 분석 결과를 고객이 이해하기 쉽게 설명해야 하는 소통의 어려움이 있습니다.

마지막으로 분석 결과를 검토하고 다른 사람에게 설명하려면 근거가 필요한데, 이를 확인하고 공유하기가 쉽지 않습니다. 결국 저희가 해결하고 싶었던 건, 고객의 요청에 명확한 근거를 바탕으로 답변하는 일이었습니다. 그 고민을 가장 잘 보여주는 질문이 있습니다.

"이 기능, 되나요?" 고객의 질문에서 시작해 실제 시스템을 분석하고, 근거를 바탕으로 답변한다는 의미를 담아 '되나AI'라고 이름을 지었습니다.

THE PLATFORM
그래서, 되나AI를 만들었습니다

고객의 요구사항 한 줄에서,
근거 있는 견적까지.

CORE 1

영향 범위를 한눈에

요구사항이 영향을 주는 기능·화면·파일을 실제 소스 코드와 DB 구조에서 찾아, 근거와 함께 알려줍니다.

CORE 2

눈높이에 맞는 결과

고객이 이해하기 쉬운 한 줄 요약과, 개발자가 확인할 기술 분석 내용을 함께 제공합니다.

CORE 3

근거와 함께 검토

분석 결과와 관련 근거를 함께 제공하고, 담당자가 승인하거나 반려하며 최종 판단은 사람이 내립니다.

원칙실제 시스템을 분석하고, 근거를 제시하며, 사람이 검토합니다.
※ 현재 구현 범위는 요구사항의 영향 분석과 검토까지이며, 견적 산출은 다음 목표입니다.

요구사항 한 줄에서 근거 있는 견적까지가 저희가 바라보는 방향이고, 현재 구현된 범위는 영향 분석과 검토까지입니다.

저희 되나 AI는 고객의 요구사항이 영향을 주는 범위를 실제 소스 코드와 DB 구조에서 찾아서, 근거와 함께 알려줍니다.

고객은 이해하기 쉬운 한 줄 요약을, 개발자는 확인할 기술 분석 내용을 함께 볼 수 있습니다.

분석 결과와 관련 근거를 함께 제공하고, 담당자가 승인하거나 반려합니다. 최종 판단은 사람이 내리도록 구현했습니다.

정리하면, 되나AI는 실제 시스템을 분석하고, 근거를 제시하며, 사람이 최종 검토합니다.

HOW IT WORKS
되나AI는 어떻게 답할까요?

먼저 근거를 준비하고, 필요한 근거를 찾아 답변합니다.

1

프로젝트 사전 분석

소스와 DB 구조에서 근거를 만들어 저장해 둡니다

소스 코드 · DB 구조 분석›분석 정보 저장 · 색인
2

질문에 맞는 근거 검색

RAG: 질문과 관련된 근거만 골라냅니다

사용자 질문 (요구사항)›관련 소스·DB 정보 검색
3

근거 기반 답변 생성

근거와 함께 쉬운 요약과 기술 분석을 만듭니다

질문 + 검색된 근거›AI 분석 결과 생성
프로젝트 분석부터 질문에 맞는 근거 검색까지, 더 정확한 AI 답변을 위한 기반을 만듭니다.
※ DB는 구조만 읽기 전용으로 읽습니다. 근거가 적은 작은 프로젝트는 전체 근거를 그대로 전달합니다.

그러면 되나AI는 어떻게 필요한 근거를 찾을까요?

먼저 프로젝트를 등록하면 실제 소스 코드와 DB 구조를 조회해 구조와 연결 관계를 분석하고, 그 근거를 저장해 검색할 수 있게 색인해 둡니다.

그다음, 고객이나 개발자가 요구사항을 질문하면 프로젝트 전체를 다시 보지 않고, 질문과 관련된 소스 코드와 DB 정보만 검색합니다.

마지막으로 질문과 검색된 근거를 함께 AI 모델에 전달해 답변을 생성합니다.

정리하면, 프로젝트 분석부터 질문에 맞는 근거 검색까지, 더 정확한 AI 답변을 위한 기반을 만듭니다.

분석에 사용

저희 시스템은 총 5개의 서버로 구성되어 있으며, 각 서버가 서로 역할을 나누어 동작하고 있습니다. 먼저 각 서버가 어떤 역할을 담당하는지 핵심 기능 위주로 간략하게 설명드리겠습니다. 이후 전체 구성도를 통해 각 서버가 어떻게 연결되어 데이터를 주고받고, 최종적으로 분석 결과를 만들어 내는지 전체적인 동작 흐름을 설명드리겠습니다.

웹서버는 사용자가 서비스 화면을 통해 기능을 이용할 수 있도록 제공하는 역할을 담당합니다.

서비스 서버는 프로젝트 등록 시 소스코드와 데이터베이스 구조를 수집하고, 이를 분석에 필요한 하나의 데이터로 정리해 AI 분석 서버에 전달합니다.

AI 분석 서버는 크게 프로젝트 등록 단계와 고객의 요구사항을 분석하는 단계로 나뉩니다. 먼저 프로젝트 등록 단계에서는 서비스 서버로부터 프로젝트의 소스코드와 데이터베이스 정보가 담긴 JSON 데이터를 전달받습니다. 이후 전달받은 데이터를 작은 단위로 나누는데, 이때 두 가지 형태로 가공해 SQLite에 저장합니다. 첫 번째는 데이터를 검색하기 쉽도록 토큰 단위로 나누어 저장하는 것이고, 두 번째는 임베딩 모델을 활용해 각 데이터의 의미를 숫자로 표현한 벡터 데이터로 변환해 함께 저장하는 것입니다. 이렇게 프로젝트별 분석 자료를 미리 저장해 둡니다.

다음으로 고객이 프로젝트에 대한 기능 변경이나 개선 요청을 하면, 전체 JSON 데이터를 다시 AI 모델에 전달하는 것이 아니라 SQLite에 저장해 둔 데이터 중에서 고객의 요구사항과 관련성이 높은 자료만 검색하고, 이를 추출해 AI 모델에 전달합니다. 이를 통해 불필요한 데이터 전달을 줄이고, AI가 실제 요구사항과 관련된 근거를 중심으로 분석할 수 있도록 합니다.

모델 실행 엔진은 두 가지 일을 하는데요. 하나는 분석 모델이 요청서를 읽고 답변을 만드는 일이고, 다른 하나는 임베딩 모델이 글을 숫자로 바꾸는 일입니다.

마지막은 AI 학습 서버입니다. 분석과는 따로 동작하는 별도의 서버로, 사람이 승인한 사례로 모델을 학습시키고 서비스에 쓸 수 있는 파일로 변환합니다.

이제 각 서버가 어떻게 연결되어 동작하는지 전체 시스템 흐름을 살펴보겠습니다. 전체 흐름은 크게 세 가지로 나뉩니다. 첫 번째는 프로젝트를 등록하고 분석에 필요한 자료를 수집하고 저장하는 흐름, 두 번째는 고객이 요구사항을 입력하면 관련 자료를 검색해 분석하는 흐름, 마지막은 분석 모델을 프로젝트 목적에 맞게 학습시키는 흐름입니다. 먼저 프로젝트 등록 흐름부터 살펴보겠습니다. 프로젝트 등록 시 접속 정보를 입력하면 서비스 서버가 소스와 데이터베이스 구조를 읽고 분석 자료를 만듭니다. AI 분석 서버는 이 자료를 작게 나눠 숫자와 함께 보관하고, 모델에게 자료 전체를 보내 분석하게 합니다. 돌아온 결과는 확인한 뒤 서비스 서버에 저장되고, 화면에서 저장된 결과를 확인합니다.

다음은 고객이 요구사항을 입력했을 때의 처리 과정입니다. 먼저 서비스 서버에서 해당 프로젝트 정보와 고객의 요구사항을 AI 분석 서버로 전달합니다. AI 분석 서버는 고객의 요구사항을 하나의 문장으로 정리한 뒤, 임베딩 모델을 통해 숫자로 변환합니다. 이렇게 변환한 데이터와 기존 SQLite에 저장해 둔 프로젝트 자료를 비교합니다. 이때 단어의 일치도와 의미적 유사도를 함께 활용해 요구사항과 관련성이 높은 자료만 찾아 분석 모델에 전달합니다. 이후 분석 모델은 총 3번에 걸쳐 순차적으로 분석을 진행합니다. 첫 번째는 요구사항으로 인해 소스코드의 어느 부분에 영향이 있는지 분석하고, 두 번째는 데이터베이스의 변경이 필요한지 검토합니다. 마지막으로 앞선 두 분석 결과를 종합해 최종 답변을 생성합니다. 이처럼 분석을 세 단계로 나눈 이유는 소스코드와 데이터베이스의 영향도를 각각 검토하고, 그 결과를 종합해 보다 정확한 답변을 제공하기 위해서입니다. 다만 현재는 이 세 가지 분석을 병렬로 처리하는 것이 아니라 하나씩 순차적으로 진행하고 있습니다. 여기에 모델이 실행되는 Mac Studio의 하드웨어 성능적인 한계까지 더해져 현재는 분석에 다소 시간이 소요되고 있습니다. 각 분석 단계에서는 응답이 정상적으로 생성되었는지 검증하는 과정도 거치며, 최종 분석 결과는 저장됩니다. 이후 담당자가 결과를 검토해 승인하거나 반려할 수 있도록 구성했습니다.

마지막은 모델 학습 흐름입니다. 승인된 사례로 학습하고, 서비스에 쓸 수 있는 파일로 바꿔 모델을 등록해 분석에 사용합니다. 지금까지 전체 시스템의 구성과 동작 흐름을 살펴봤습니다. 이어서 이러한 흐름이 실제 서비스에서 어떻게 구현되고 동작하는지 시연 영상을 통해 보여드리겠습니다.

현재는 고객의 요구사항을 분석하기 위해 AI가 여러 작업을 수행하는데, 각 작업을 순차적으로 하나씩 처리하고 있습니다. 앞으로는 동시에 처리할 수 있는 작업들을 병렬로 실행하도록 개선해 전체 대기 시간을 줄이고자 합니다.

위 그림이 지금 방식입니다. 일반 분석이 끝나야 데이터베이스 검토를 시작하고, 테이블이 많으면 묶음으로 나눈 검토도 하나가 끝나야 다음 것을 합니다. 그래서 기다리는 시간이 계속 이어집니다.

아래 그림이 개선할 방식입니다. 서로 상관없는 일은 동시에 시킵니다. 일반 분석과 데이터베이스 묶음 검토를 한꺼번에 시작하고, 마지막에 합치는 일만 순서를 지킵니다. 작업을 동시에 진행하면 개별 작업의 처리 시간은 다소 늘어날 수 있지만, 전체 대기 시간은 줄어듭니다. 이 그림은 이해를 돕기 위한 예시입니다.

바꾸는 일은 세 가지입니다. 묶음 검토를 동시에 시키고, 일반 분석과 데이터베이스 검토를 함께 시작하고, 한꺼번에 보내는 개수에 상한을 둡니다.

다만 AI 모델은 장비 한 대에서 돌아가기 때문에, 동시에 처리할 수 있는 만큼만 빨라집니다. 그래서 먼저 장비의 한계를 측정한 뒤에 적용하려고 합니다.

분석할 때 골라서 붙이기

요청이 오면 그 프로젝트의 맞춤 파일을 붙여 분석합니다.

조건승인된 사례가 충분히 쌓인 프로젝트부터 적용하고, 효과는 정답 세트로 확인합니다.

두 번째 개선은 프로젝트마다 맞춤으로 쓰는 것입니다.

먼저 지금 방식과 개선 방식을 비교해 보겠습니다.

지금은 AI 모델 하나를 모든 프로젝트가 같이 씁니다. 학습할 때도 프로젝트 구분 없이 자료를 합쳐서 학습합니다. 그래서 프로젝트마다 코드와 규칙이 다르면 한 모델에 전부 반영하기 어렵습니다.

개선 방식은 이렇습니다. 기본 AI 모델은 지금처럼 하나로 공유하고, 학습 결과만 프로젝트별 파일로 분리합니다. 분석할 때는 그 프로젝트의 학습 파일을 기본 모델에 붙여서 사용합니다. 이렇게 하면 프로젝트마다 모델을 새로 만들 필요가 없고, 프로젝트별 학습 자료를 따로 관리할 수 있습니다.

이를 위해 크게 세 가지 작업이 필요합니다. 첫 번째로 학습 자료를 프로젝트별로 구분해 학습하고, 두 번째는 각 프로젝트가 어떤 학습 파일을 사용하는지 연결 정보를 관리합니다. 마지막으로 분석 요청이 들어오면 해당 프로젝트에 맞는 학습 파일을 적용하도록 개선할 예정입니다.

다만 모든 프로젝트에 한 번에 적용하기보다는 승인된 분석 사례가 충분히 쌓인 프로젝트부터 단계적으로 적용할 계획입니다. 또한 정답이 정해진 테스트 데이터를 활용해 실제 분석 정확도가 개선되었는지도 검증하겠습니다. 궁극적으로는 프로젝트마다 축적된 분석 경험을 바탕으로 더 정확한 영향도 분석과 견적 산출까지 이어가는 것이 목표입니다.
