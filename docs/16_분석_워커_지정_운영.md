# 분석 요청을 받은 백엔드에서 처리하기

## 처리 원칙

분석 요청을 받은 백엔드 인스턴스가 Git·DB 근거를 수집하고 AI 분석/추론 서버에 분석을 요청한다. 공유 데이터베이스의 작업을 다른 백엔드가 선점해 처리하지 않는다. AI 분석/추론 서버는 원래 설계에 포함된 분석 서비스이며, 이 변경은 AI 분석/추론 서버의 배치를 바꾸지 않는다.

백엔드가 시작될 때마다 고유한 인스턴스 ID를 만든다. 새 분석 작업에는 이 ID를 `target_worker_id`로 저장하고, 해당 인스턴스의 워커만 같은 ID로 작업을 선점한다. 선점한 ID는 `claimed_by_worker_id`에 남는다. 재시작하면 새 ID를 발급하므로 예전 인스턴스의 대기 작업을 새 인스턴스가 임의로 처리하지 않는다.

새 작업은 `PROJECT_SCAN_V2` 종류를 사용한다. 구버전 워커는 이 종류를 조회하지 못한다. 다른 서버가 분석 작업을 처리하는 일을 막으려면 분석 요청을 받을 수 있는 모든 백엔드에 이 코드를 배포해야 한다.

## 적용과 운영

1. [011_analysis_worker_routing.sql](../supabase/migrations/011_analysis_worker_routing.sql)을 공유 Supabase DB에 한 번 적용한다. 기존 분석 작업은 삭제하거나 새 종류로 바꾸지 않는다. 이 프로젝트의 공유 DB에는 2026-10-15에 적용했다.
2. 분석 요청을 받는 모든 백엔드에 새 코드를 배포하고 `DOENAAI_ANALYSIS_WORKER_ENABLED=true`로 실행한다. 새 코드의 기본값도 `true`다. 인스턴스 ID를 수동으로 맞추지 않는다.
3. 워커를 명시적으로 끈 백엔드는 새 분석 요청을 `503`으로 거절한다. 작업을 다른 백엔드에 넘기지 않는다.
4. Git·DB 연결 정보와 AI 분석/추론 서버 접속 설정은 요청을 받는 각 백엔드에서 유효해야 한다. 설정을 갖추지 못한 인스턴스는 분석 요청을 받지 않도록 운영한다.
5. 서버 재시작 전에 진행 중인 작업이 끝났는지 확인한다. 재시작 뒤에는 새 인스턴스 ID가 발급된다. 중단된 실행 작업은 제한 시간이 지나면 실패로 종료되며 다른 서버에서 자동 재시도하지 않는다. 예전 인스턴스의 대기 작업은 자동으로 옮기지 않으므로 상태를 확인해 취소하고 새로 요청한다.

`DOENAAI_ANALYSIS_WORKER_ID`와 `DOENAAI_ANALYSIS_TARGET_WORKER_ID`는 더 이상 사용하지 않는다. 모든 서버에 `primary`를 지정하는 방식은 요청을 받은 곳과 처리하는 곳이 달라질 수 있으므로 금지한다.

## 확인 SQL

```sql
select id, analysis_type, status, target_worker_id, claimed_by_worker_id,
       created_at, started_at, completed_at
from public.analysis_jobs
order by created_at desc
limit 10;
```

새 작업의 `analysis_type`은 `PROJECT_SCAN_V2`여야 한다. 선점 뒤에는 `target_worker_id`와 `claimed_by_worker_id`가 같아야 하며, 요청을 받은 백엔드 시작 로그의 `Analysis worker ready: instanceId=` 값과도 같아야 한다. 비밀번호·토큰은 로그와 문서에 남기지 않는다.

## 변경 전 확인 기록

2026-10-15에 Mac 백엔드가 `primary`로 작업 `3ff1eb10-ea36-44c7-a2e0-feb350474984`를 선점하고 AI 분석을 시작한 것은 확인했다. 이 작업은 약 10분 뒤 AI 요청 단계에서 실패했다. 이 기록은 공통 `primary` 방식의 동작 확인이며, 요청 인스턴스별 라우팅 검증 결과로 취급하지 않는다. AI 응답 실패 원인은 라우팅 검증과 별도로 확인해야 한다.

## 인스턴스별 라우팅 검증

2026-10-15에 Mac 백엔드를 새 코드로 재시작했고, 시작 로그에 `instanceId=714b5814-294c-4867-89c8-f1983e0aa316`이 기록됐다. 기존 테스트 변경요청의 새 분석 작업 `0be1b64d-49c4-4812-b826-35c9c498b79c`는 DB에서 `PROJECT_SCAN_V2`, `RUNNING`으로 확인됐다. `target_worker_id`와 `claimed_by_worker_id`가 모두 위 인스턴스 ID와 같았다. Git·DB 수집과 AI 요청 단계 진입을 화면에서 확인한 뒤 검증용 작업을 취소했고, 화면에 `분석 취소`가 표시됐다. 다른 백엔드에서 같은 작업을 처리하지 못한다는 점은 코드의 인스턴스별 선점 조건과 테스트로 확인했으며, 두 백엔드를 동시에 실행한 실제 경쟁 검증은 별도로 필요하다.
