# 되나AI 발표 예상 질문과 답변

발표 후 질의응답에서 나올 만한 질문을 서비스, 정확도, 모델, 학습, 보안, 한계 순으로 정리했습니다.
답변은 현재 구현된 내용과 `docs`의 구조 문서를 기준으로 했고, 아직 검증하지 못한 부분은 그대로 밝히도록 썼습니다.

## 서비스와 필요성

### Q1. ChatGPT 같은 범용 AI에 소스를 넣어도 되는 것 아닌가요? 되나AI는 무엇이 다른가요?

범용 AI는 소스 전체를 알지 못하고, 답의 근거를 남기지 않습니다. 되나AI는 먼저 프로그램이 Git 소스와 DB 구조에서 파일, 연결 관계, 호출 주소, 테이블과 컬럼을 사실로 수집하고, AI는 그 근거만으로 영향 범위와 위험을 해석합니다. 결과마다 근거를 남기고, 분석 시점의 커밋을 고정해 같은 결과를 다시 볼 수 있습니다. 최종 판단은 담당자가 합니다.

### Q2. 실제로 업무가 얼마나 줄었나요? 수치가 있나요?

현재 확인한 것은 실제 프로젝트의 긴 분석이 끝까지 완료되어 결과 화면까지 나온 것입니다. 시간 절감 비율은 아직 측정하지 않았기 때문에 수치로 말씀드리지 않겠습니다. 발표에 나온 업무 비중은 저희 팀의 경험에 기반한 예시입니다. 개선 사항에서 말씀드린 처리 속도도 먼저 측정한 뒤 적용할 계획입니다.

### Q3. 누가 쓰는 서비스인가요?

PM은 요구사항을 정리하고 결과를 검토해 일정과 비용을 판단합니다. PL과 개발자는 소스와 DB 근거를 확인합니다. 모델 운영자는 승인된 자료로 모델을 학습시키고 적용합니다. 관리자는 사용자와 권한을 관리합니다. 고객에게는 확정된 결과만 제한된 범위로 보여주는 것이 목표입니다.

## 분석 방식과 정확도

### Q4. AI가 틀린 답을 하면 어떻게 하나요? 정확도는 얼마인가요?

정확도는 아직 검증 중이라 수치로 말씀드리기 어렵습니다. 대신 틀릴 수 있다는 전제로 설계했습니다. 근거가 없으면 단정하지 않고 확인이 필요하다고 표시하고, 입력이 잘리거나 수집하지 못한 범위는 경고로 보여줍니다. 위험 점수는 판단 보조값일 뿐이고, 담당자가 근거를 확인해 승인, 반려, 수정합니다. 승인과 수정 내용은 기록으로 남깁니다.

### Q5. AI가 없는 사실을 지어내는(환각) 문제는 어떻게 막나요?

모델에게 소스 전체를 맡기지 않고, 프로그램이 수집한 근거만 전달합니다. 모델 응답은 정해진 JSON 형식으로 검사합니다. 환각을 완전히 없앨 수는 없기 때문에, 결과에 파일과 줄 위치 같은 근거를 함께 보여줘서 사람이 바로 대조할 수 있게 했습니다.

### Q6. 소스가 아주 큰 프로젝트는 어떻게 처리하나요? 모델 입력 길이 제한이 있지 않나요?

입력 크기에 상한을 둡니다. 백엔드 기본 상한은 9만 자이고 설정으로 조정할 수 있습니다. 그리고 요구사항이 있으면 근거를 전부 보내지 않고, 요구사항과 관련 있는 조각만 골라서 보내는 RAG 방식을 씁니다. 근거를 항목 단위 조각으로 저장해 두었다가 BM25와 의미 유사도 점수로 관련 조각을 고릅니다. 실제로 얼마나 보냈고 무엇이 생략됐는지는 결과의 경고와 범위 정보로 확인할 수 있습니다.

### Q7. RAG에 벡터 검색(임베딩)을 쓰나요? BM25만으로 충분한가요?

네, 둘을 함께 씁니다. 기본은 BM25로, 외부 라이브러리 없이 직접 구현했고 글자가 겹치는지를 기준으로 점수를 냅니다. 여기에 임베딩 모델(bge-m3)로 계산한 의미 유사도를 섞어서, 고객이 쓴 한글 요구사항과 소스의 영어 이름처럼 글자가 겹치지 않는 경우도 찾습니다. 두 점수를 평균 내고, 유사도가 너무 낮은 조각은 버립니다. 임베딩 모델이 설치되어 있지 않거나 호출이 실패하면 BM25만으로 동작하고 경고를 남깁니다.

### Q8. 동적 SQL이나 프레임워크 내부 호출처럼 코드에 드러나지 않는 관계도 찾나요?

찾지 못합니다. 현재 수집기는 기술 선언, 소스 참조, 명시적인 DB 매핑을 찾는 정적 분석입니다. 모든 호출 관계나 컬럼별 사용 위치를 완전히 추적하지는 않습니다. 그래서 수집되지 않은 관계를 영향이 없다고 해석하지 않고, 확인이 필요한 항목으로 남기도록 했습니다.

## 모델과 서버 구성

### Q9. 어떤 AI 모델을 쓰나요? 왜 외부 서비스가 아니라 자체 서버인가요?

현재는 Qwen을 기본 모델로 쓰고, 모델 실행 엔진은 Ollama입니다. 모델은 화면에서 바꿀 수 있고, 분석을 시작할 때 고른 모델은 그 분석이 끝날 때까지 유지합니다. 자체 서버를 쓰는 가장 큰 이유는 고객 소스와 DB 구조가 외부로 나가지 않게 하기 위해서입니다.

### Q10. 서버는 어떻게 구성되어 있나요?

화면은 Vue 3, 백엔드는 Java와 Spring Boot입니다. 백엔드가 인증과 권한, Git과 DB 근거 수집, 작업 관리를 맡고, AI 분석 서버는 Python FastAPI로 모델 호출과 응답 검사를 맡습니다. 학습은 별도 학습 서버에서 MLX-LM과 LoRA로 하고, 로그인은 Supabase를 씁니다. 분석처럼 오래 걸리는 일은 비동기 작업으로 접수하고 화면이 진행 상태를 조회합니다.

### Q11. 분석 서버가 한 대인데, 여러 명이 동시에 쓰면 어떻게 되나요?

모델은 장비 한 대에서 돌아가기 때문에 동시에 처리할 수 있는 만큼만 빨라집니다. 분석 요청은 작업으로 접수되어 처리됩니다. 개선 계획으로 말씀드린 병렬 처리도 장비의 한계를 먼저 측정하고, 한꺼번에 보내는 개수에 상한을 두는 방식으로 적용하려고 합니다.

## 학습과 개선

### Q12. AI 학습은 어떻게 하나요? 사용자 데이터가 그대로 학습에 쓰이나요?

자동으로 쓰이지 않습니다. 담당자가 AI 원본을 검토해 승인하거나 수정한 자료만 학습 후보가 되고, 정답과 비식별화를 한 번 더 확인한 뒤에 확정합니다. 학습은 LoRA 방식으로 기반 모델은 그대로 두고 어댑터만 따로 만듭니다. 만들어진 모델도 사용자가 응답을 검증하고 직접 적용해야 분석에 쓰입니다.

### Q13. 학습하면 정확도가 올라가는 것이 증명되었나요?

아직 증명하지 못했습니다. 학습 손실이 줄어드는 것, 어댑터가 저장되는 것, JSON 응답 검증이 통과하는 것은 각각 다른 확인이고, 이것만으로 업무 품질이 좋아졌다고 말할 수 없습니다. 그래서 정답이 정해진 테스트 데이터로 학습 전후를 같은 조건에서 비교하고 사람이 검토하는 절차를 계획하고 있습니다.

### Q14. 프로젝트마다 맞춤 학습 파일(어댑터)은 지금 되나요?

아직 계획 단계입니다. 지금은 모델 하나를 모든 프로젝트가 공유하고, 학습 자료도 프로젝트 구분 없이 합쳐서 씁니다. 기본 모델은 하나로 유지하고 학습 결과만 프로젝트별 파일로 나눠서, 분석할 때 그 프로젝트의 파일을 붙이는 방식으로 개선하려고 합니다. 승인된 사례가 충분히 쌓인 프로젝트부터 단계적으로 적용합니다.

### Q15. 학습 자료가 적은 프로젝트는 어떻게 하나요?

자료가 충분하지 않으면 학습 효과가 불안정할 수 있어서, 그런 프로젝트는 기본 모델과 근거 수집만으로 분석합니다. 맞춤 학습은 승인된 사례가 충분히 쌓인 프로젝트부터 적용하는 것이 원칙입니다. 또 같은 원 요구사항의 수정본과 후속 질문은 학습과 평가에 나눠 섞이지 않게 한쪽에 둡니다.

## 보안과 운영

### Q16. 고객 소스 코드와 DB 정보는 안전한가요?

AI는 자체 서버에서 돌기 때문에 소스가 외부 AI 서비스로 나가지 않습니다. Git과 DB의 비밀번호와 토큰은 백엔드에서 암호화해서 저장하고, 화면 응답과 모델 입력과 로그에는 넣지 않습니다. 모델이 직접 Git이나 DB 계정을 받아 코드를 실행하거나 SQL을 수행하지도 않습니다. 내부 분석 API와 모델 엔진은 인터넷에 공개하지 않습니다.

### Q17. DB는 어떻게 읽나요? 운영 데이터가 바뀌거나 노출될 위험은 없나요?

읽기 전용으로 연결해서 테이블, 뷰, 컬럼, 기본키, 외래키, 인덱스 같은 구조만 읽습니다. 업무 데이터의 행은 조회하지 않습니다. 그래서 데이터 값이 모델이나 화면으로 전달되지 않고, 데이터를 바꿀 수도 없습니다. 지원 DB는 현재 PostgreSQL과 Oracle입니다.

### Q18. 권한은 어떻게 관리하나요?

로그인은 Supabase로 하고, 최종 권한과 조직 및 프로젝트 접근 범위는 모두 백엔드에서 검사합니다. 화면에서 버튼을 숨기는 것은 편의일 뿐 권한 검사를 대신하지 않습니다. 다만 사용자별 역할을 부여하고 회수하는 관리 화면은 아직 없습니다.

### Q19. 분석 중에 서버가 멈추거나 응답이 끊기면 어떻게 되나요?

분석은 비동기 작업이라 화면을 닫아도 서버에서 계속 진행됩니다. 작업은 대기, 진행, 완료, 실패, 취소 상태로 관리하고 단계별 이력과 경과 시간을 남깁니다. 응답이 끊기면 같은 작업을 다시 만들지 않고 기존 작업의 상태부터 확인합니다. 잘못된 인증, 모델 미설치, 응답 형식 오류, 시간 초과는 구분해서 처리합니다.

## 한계와 앞으로

### Q20. 지금 가장 큰 한계는 무엇인가요?

세 가지입니다. 첫째, 정확도를 실제 업무 사례로 아직 충분히 검증하지 못했습니다. 둘째, 정적 분석이라 동적 SQL이나 프레임워크 내부 호출처럼 코드에 드러나지 않는 관계는 놓칠 수 있습니다. 셋째, 견적 작성과 고객 공개까지 이어지는 전체 흐름은 아직 구현하지 않았습니다. 지금은 새 기능보다 검증에 집중하고 있습니다.

### Q21. 견적은 어떻게 자동으로 산출하나요?

견적 산출은 다음 단계에서 만들 기능이고 지금은 구현되어 있지 않습니다. 승인된 분석 결과에서 작업 항목, 작업량, 기간, 비용으로 이어지는 방식을 계획하고 있습니다. 견적도 AI가 확정하지 않고 초안과 근거를 제공하며 PM이 최종 확정합니다.

### Q22. 다른 회사나 다른 프로젝트에도 적용할 수 있나요?

프로젝트 단위로 Git과 DB를 연결하는 구조라 다른 프로젝트에도 등록해서 쓸 수 있습니다. 다만 지원하는 DB가 PostgreSQL과 Oracle이고, 언어별 수집 정확도는 검증이 더 필요합니다. 여러 회사가 함께 쓰는 서비스 형태와 더 많은 언어와 DB 지원은 앞으로의 확장 과제입니다.

## 폐쇄망 적용

### Q23. 폐쇄망에서는 Git에 연결할 수 없는데, 소스는 어떻게 넣나요? ZIP으로 넣나요?

두 가지로 나눠 답합니다. 첫째, 폐쇄망 안에 사내 Git 서버가 있으면 그대로 연결할 수 있습니다. 현재도 사내 Git 서버와 Yona, GitLab 같은 서버를 지원하고, 접속은 HTTPS 토큰, 비밀번호, SSH 키로 합니다. 둘째, 사내에 Git 서버가 없거나 연결이 막힌 경우를 위해 ZIP 업로드를 준비하고 있습니다. 다만 ZIP 업로드는 화면에 선택지만 있고 아직 구현되지 않았으며, 다음 단계에서 추가할 계획입니다. 그래서 지금은 "사내 Git 서버 연결은 가능하고, ZIP은 개발 예정"이라고 말씀드리는 것이 정확합니다.

### Q24. 폐쇄망에 설치하면 어떤 부분이 막힐 수 있나요?

다섯 가지를 예상하고 있고, 아직 폐쇄망에서 실제로 설치해 보지는 않았습니다. (1) 로그인: 지금은 외부 서비스인 Supabase를 쓰기 때문에, 폐쇄망에서는 사내에 따로 설치하거나 다른 인증으로 바꾸는 검토가 필요합니다. (2) 모델 파일: 모델 실행 엔진 Ollama의 모델(Qwen)과 임베딩 모델(bge-m3)은 인터넷에서 받아야 하므로 외부에서 받아 파일로 반입해야 합니다. 학습 쪽은 이미 인터넷 없이 로컬 파일만 쓰도록 되어 있습니다. (3) 공유 폴더: 학습 자료와 완성 모델 전달에 iCloud Drive를 NAS처럼 쓰고 있어서, 폐쇄망에서는 사내 파일 서버로 바꿔야 합니다. (4) 설치 의존성: 백엔드, 화면, AI 서버의 라이브러리를 인터넷에서 받아 빌드하므로 사내 저장소나 사전 반입이 필요합니다. (5) DB: 사내 DB는 읽기 전용으로 직접 연결할 수 있으면 문제없고, 직접 연결이 어려우면 DDL 파일을 올리는 방식을 쓰는데 이 기능도 아직 준비 중입니다.

### Q25. 그러면 폐쇄망에서도 AI 분석 자체는 되나요?

네, 분석에 필요한 AI는 처음부터 자체 서버에서 돌리는 구조라 외부 AI 서비스를 호출하지 않습니다. 그래서 위에서 말씀드린 연결 문제만 해결하면 분석 자체가 외부 인터넷에 의존하지 않습니다. 다만 앞서 말씀드린 대로 폐쇄망 환경에서의 설치와 동작은 아직 직접 검증하지 못했습니다.

## 답변할 때 유의할 점

- 수치(시간 절감, 정확도)는 측정한 값이 아직 없으므로 지어내지 않고 "검증 중"이라고 답합니다.
- 병렬 처리와 프로젝트별 맞춤 학습은 구현 완료가 아니라 개선 계획이라고 분명히 말합니다.
- ZIP 업로드와 DDL 업로드는 아직 준비 중인 기능이라고 밝히고, 폐쇄망 설치는 직접 검증하지 못했다고 말합니다.
- 마무리는 "AI는 근거를 제공하고 최종 판단은 사람이 합니다"로 돌아옵니다.
