### 2026-10-19 서버 명칭 정리

화면·설정·전송 상태·오류 안내와 문서의 명칭을 웹 화면(프론트엔드·Web),
서비스 서버(백엔드·WAS), AI 분석/추론 서버(`ai-server`), AI 학습 서버(`training`)로 통일했다.
Mac Studio와 MacBook은 기준 장비 사양과 당시 시험 기록을 설명할 때만 사용한다.
실행 경로·환경변수·API 주소·상태 코드는 같은 값을 사용하며, 이 명칭 변경이
학습 완료나 배포 완료를 뜻하지는 않는다. 팀 설명용 명칭과 역할은
[온보딩 가이드](07_팀원_온보딩_프로젝트_설명.md)의 대응표를 따른다.

설명용 서버 구성도에 Mac Studio M1 Max·CPU 10코어·GPU 32코어·통합 메모리 64GB와
MacBook Pro M4 Max·CPU 16코어·GPU 40코어·통합 메모리 64GB를 표시했다.
MacBook Pro 상세 사양은 2026-10-19 사용자가 전달한 장비 확인값이다.
공유 NAS 역할은 iCloud Drive로 구현한 파일 공간으로 구분하고,
학습 사례 게시→파일 동기화·수신→평가된 모델 배포 경로를 표시했다.
장비의 CPU·GPU 상세 사양은 온보딩 가이드에 기록하며 뉴럴 엔진 사용을 가정하지 않는다.

모델 배포도 SSH 직접 전송 대신 공유 NAS 역할의 iCloud Drive를 거치는 방향으로 결정했다.
AI 학습 서버가 버전별 배포 파일을 게시하고 AI 분석/추론 서버가 가져와 무결성·호환성·시험 응답을
검증한 후 승인된 모델만 적용한다. 중단 시 재시도하고 기존 Qwen을 유지하는 원칙은
[모델 배포 방침](../training/MODEL_DELIVERY.md)에 기록했다.
현재는 방침 정리 단계이며 모델 자동 게시·가져오기·전환·되돌리기는 아직 구현하지 않았다.

새 분석은 원래 일반 분석 단계 응답을 `facts.generalAnalysis`에 따로 보존한다.

기존 편집값은 덮어쓰지 않으며 보완 후에는 사람 검토 확인란을 다시 선택한다.
누락 안내는 현재 JSON에 맞춰 갱신하고 주요 누락값이 있으면 전송을 막는다.

DB 수집 완료 기록의 시각과 DB 관련성·이유가 보완된 화면도 확인했다.
AI 학습 서버의 수신 계약과 현재 기본 Qwen 설정은 바꾸지 않았다.

원래 입력의 정확한 파일·줄 참조에 없어서 거부된 것을 확인했다. 원문을 수정하지 않고
학습 사례 사본에만 원본 커밋의 검증된 근거를 보강하는 경로를 추가했다.
화면에서 불일치 파일·줄 번호를 표시하고 원본 커밋 근거 확인·보강과 전송 전 전체 검사를 제공한다.

재시작 후 근거 보강과 전체 검사에서 발생한 400은 Backend 로그에서

보강·검사용 `TrainingCaseRequest`를 분리했으며 실제 전송의 게시 동의 검사는 유지한다.

다른 사례 거부를 확인했다. 이 수정은 Backend 재시작이 필요하며 실제 사례 재시도는 별도로 확인해야 한다.

이후 실제 승인 사례의 원본 커밋 근거 보강과 전송 전 전체 검사 통과를 화면에서 확인했다.

수신함 조회는 `READY_FOR_DATASET`·파일 1개·사례 1건을 반환했다. 이는 데이터 전달 완료이며 모델 학습 완료는 아니다.

검토 상세, 승인·반려, 학습 사례 편집·보강·검사·전송은 별도 모달에서 수행한다.
모달은 작은 화면의 너비·높이에 맞추고 내부만 스크롤하며 제목과 닫기 버튼을 고정한다.
배경 조작·초점 이탈을 막고 처리 중에는 닫기를 제한한다. 모달을 닫아도 현재 화면의
미전송 초안은 유지하지만 새로고침·다른 화면 이동 뒤의 보존은 제공하지 않는다.
실제 Safari에서 요약 카드, 모달 열기와 Escape로 닫기를 확인했다. 이 화면 변경은 Web 갱신만 필요하다.

첫 사용자의 이해를 돕도록 화면 명칭을 분석 결과 검토·승인 완료·결과 검토·학습 데이터 관리로 바꿨다.

전송 상태와 상태 확인 버튼은 하나의 카드로 묶고, 준비·검사·전송·접기 버튼의 역할과 간격을 구분했다.
초안 내려받기는 선택형 접기 영역으로 옮겨 웹 검토·전송에 필수인 것처럼 보이지 않게 했다.

## 2. 실제 구현된 분석 흐름

```text
프로젝트 등록: 조직 선택/생성 → 프로젝트 저장 → Git·DB 연결 시험/저장
변경 분석: 프로젝트별 변경요청 테이블 검색 → 필요 시 등록 폼에서 Git 프로젝트 선택·요구사항/첫 버전 생성 → 현재 버전 ID 선택
공통: 요청 백엔드의 인스턴스 ID로 작업 PENDING 생성 → 지정된 Worker만 선점 RUNNING
  → 고정 Git commit 읽기 → 읽기 전용 DB 구조 → SQL/ORM 참조 → 입력 범위 검사
  → FastAPI → Qwen 전체 분석
  → 요구사항의 DB 관련성에 따라 DB 호출 생략 또는 추가 분석
  → 응답 재검증 → 결과·실제 전달 facts 저장 + COMPLETED
  → Frontend job별 polling 및 결과 조회 → 필요 시 추가 질문/새 버전 재분석
  → 권한 있는 사람이 AI 원본 승인·수정본 승인·반려 중 하나를 한 번 기록
```

Worker는 Backend 프로세스 안에서 실행한다. AI 분석/추론 서버는 Git/대상 DB에 직접 접속하지 않는다.
대상 DB의 업무 데이터 행을 모델로 보내거나 변경 SQL을 실행하지 않는다.
소스→DB 수집은 순차 처리이며 화면의 자동 상태 조회가 동시에 동작한다.
진행률 80%는 모델 대기 구간에도 나타나므로 시간 비율이나 남은 시간으로 해석하지 않는다.
화면은 서버 진행률을 임의로 높이지 않고 단계 활동·경과 시간으로 대기 중임을 보여준다. Backend Worker는 공개용 고정 문구의 단계 시작·완료 내역을 `analysis_jobs.analysis_options.activityLog`에 저장하고, 기존 작업 상태 API의 약 2.5초 조회로 최신 작업 내역을 보여준다. 최신 10건만 펼쳐 놓고 이전 내역은 접는다. AI 응답 대기가 길어지면 Backend가 30초마다 대기 중임을 기록하고 현재 단계 경과 시간은 매초 갱신한다. 이 기록은 **Backend가 응답을 기다린다는 뜻이지 모델 계산 완료율을 증명하지 않는다.** 원본 서버 로그·접속 정보·예외 내용은 화면에 전달하지 않는다. **모델 내부 토큰 진행률이나 남은 시간 예측은 아직 제공하지 않는다.**
AI 분석/추론 서버는 내부 키로 보호된 `/api/analysis/project/stream`에서 일반 영향 분석과 필요 시 DB 영향 분석의 시작·완료 및 응답 형식 재시도를 안전한 코드로 순차 전달한다. Backend가 이 코드를 사용자용 문구로 바꿔 같은 작업 내역에 저장한다. 구버전 AI 분석/추론 서버가 스트림 경로를 제공하지 않으면 기존 최종 JSON 경로로 대체하며, 이때 AI 내부 단계 내역은 나타나지 않는다. 단계 내역을 보려면 AI 분석/추론 서버·Backend가 모두 이 기능을 포함한 코드로 실행돼야 한다.
2026-10-14 로컬 재검증에서 AI 분석/추론 서버·Backend를 새 코드로 재시작했다. 실제 Qwen에 DB 저장 없는 최소 구조 분석을 스트림으로 요청하자 15·30·45·60초 heartbeat 후 약 66초에 `GENERAL_COMPLETED` → `DATABASE_SKIPPED` → 최종 결과가 도착했다. 최초 실행에서는 Python 3.9의 `asyncio.TimeoutError`를 처리하지 못해 15초에 연결이 끊겼으며, 이를 수정하고 회귀 테스트를 추가했다. AI 분석/추론 서버 테스트 44개가 통과했다. **당시 시험은 AI 스트림 경로만 검증했다.** 이후 2026-10-15 실제 완료 화면은 5절에 별도로 기록했다.
저장된 결과를 여는 `GET`은 모델을 다시 호출하지 않는다. 새 요구사항으로 분석을 시작할 때는 새 AI 판단이 필요하지만, 고정 Git SHA가 같고 현재 읽기 전용 DB 구조가 저장된 완전한 근거와 일치하면 Git 체크아웃·소스 재스캔을 생략한다. **DB 변경 여부 확인을 위한 구조 메타데이터 조회는 매번 수행**한다. 이전 소스/AI 입력/DB 수집이 잘렸거나 구조가 다르면 새로 수집하며, 재사용한 원본 작업 ID는 `analysis_jobs.analysis_options`에 남긴다.
요구사항 화면에서 **저장된 근거로 바로 분석**을 선택하면 완료된 작업의 소스·DB 근거를 기준으로 새 요구사항을 AI에 다시 분석시킨다. 이 방식은 사용자가 Git·DB에 변경이 없음을 확인해야 시작되며, **현재 Git·DB를 조회하지 않으므로 변경 여부를 자동 보증하지 않는다.** 후보는 수집 범위가 잘리지 않고 경고가 없는 완료 결과만 표시한다. 기본 선택인 **최신 Git·DB 확인**은 기존의 자동 비교 경로다.
분석 화면의 **이력으로 나가기**와 브라우저 뒤로가기·다른 화면 이동은 화면 조회만 중단하고 서버 작업은 유지한다. 진행 중에는 이동 확인을 보여준다. 새로고침·탭/창 닫기는 브라우저 기본 이탈 경고를 요청하지만 브라우저 설정에 따라 표시가 제한될 수 있으며, 종료 중 비동기 취소 요청은 보내지 않는다. **분석 작업 취소**는 `PENDING`/`RUNNING`을 `CANCELLED`로 변경하며 결과 저장을 막는다. 같은 Backend 인스턴스의 실행 스레드는 중단을 시도하지만, 여러 인스턴스나 원격 모델 계산이 즉시 멈춘다고 보장하지 않는다.
취소·실패한 후속 분석은 이전 완료 결과의 질문으로 돌아가 답을 수정하거나, 같은 답이라면 새 요구사항 버전을 늘리지 않고 재시도할 수 있다. 새 분석마다 위험 점수와 등급을 다시 산정하고, 불확실성이 해소돼도 변경 자체의 데이터·보안 위험을 자동으로 낮추지 않는다. 저장된 옛 결과의 점수·등급 불일치는 화면에서 점검 필요로 표시한다.
`PROJECT_SCAN_V2` 작업은 `target_worker_id`가 지정된 요청 백엔드만 선점하며, 선점한 `claimed_by_worker_id`를 남긴다. 다른 백엔드로 자동 인계하지 않는다. 적용·장애 처리·검증 기록은 [16번 문서](16_분석_워커_지정_운영.md)에 있다. 고착 작업을 실패 처리하는 로직이 있는 것과 lease/heartbeat·자동 재시도가 구현된 것은 다르다.
사람 검토에서는 AI 원본을 보존하고 승인/반려·검토자·시각·이유·선택적 수정 결과를 별도로 저장한다. 수정 JSON의 형식·크기·비밀정보 필드·위험 점수 일관성은 검사하지만 **파일/DB 근거의 사실 여부는 자동 보증하지 않으므로 승인자가 직접 확인**해야 한다. 한 번 저장한 검토 결정은 변경할 수 없다.

## 3. 현재 Backend API 범위

| 영역 | 구현 경로 |
|---|---|
| 사용자 | `GET /api/auth/me` |
| 조직 | `GET/POST /api/organizations`, `GET /api/organizations/{id}` |

## 4. Frontend에서 먼저 보완할 부분

전체 화면별 판정과 파일 근거는 [13번 Frontend 점검](13_2026-10-14_Frontend_구현_점검.md)을 기준으로 한다.

1. **프로젝트 목록·상세·수정:** 소스 종류·브랜치 표시와 논리 삭제·복구, 상세 이동, 기본정보와 Git·DB 연결 계정 수정 화면을 연결했다. 실제 계정으로 연결 시험→저장→재조회 및 권한을 검증하고, 기술 스택 `stack`의 실제 근거 매핑과 Git 주소 변경·연결 저장의 원자화를 후속 처리한다.
2. **이력·실결과 경로:** 이력 목록·특정 job 재열기는 구현했다. 새 API의 실제 계정·브라우저 검증을 하고, 전역 아키텍처·영향도 데모를 실제 저장 결과로 연결한다.
3. **요구사항 버전·상태·검토·승인:** 추가 질문·새 버전 재분석과 결과 승인/반려 화면은 구현됐다. 우선 취소·실패 후 복원, 권한별 검토, 수정 JSON 검증을 실제 환경에서 시험한다. 과거 버전 조회·상태 변경 UI는 이후 범위다.
4. **오류·Mock 표시·미완성 버튼:** 없는 API·실행 미연결 버튼을 실제 기능처럼 표시하지 않고 빈 상태·실패·재시도·권한 거부를 처리한다.
5. **대시보드·조직·견적·고객 공개:** 각각 API/응답 정책과 UI를 기능 단위로 구현한다.
6. **모델·문서·설정 관리:** 운영 비밀의 서버 관리, 실제 학습/배포·업로드/RAG·권한을 갖춘 뒤 전환한다.
7. **검사·성능:** 최근 프론트 전체 lint·테스트·빌드 결과를 다시 확인하고, route lazy load와 실제 화면별 테스트는 이후 범위로 둔다.

학습 데이터 준비를 기다리는 동안에도 제품·Frontend 개발은 진행할 수 있다. 위 진행 화면 및 이력 재열기는 코드에 반영됐으므로 MacBook에서 중복 구현하지 말고 실제 연결을 검증한다.

## 8. 추가 질문·답변 이어 분석

- 분석 결과의 `databaseImpact.openQuestions`에 사용자가 답하거나 자유 형식 질문을 추가하면, 이전 결과를 수정하지 않고 **같은 요구사항의 새 버전**을 만든다. 새 버전의 `parent_version_id` 외래키는 이전 버전을 직접 가리키며, 질문 식별자는 모델 문장이 아닌 `분석 작업 ID + 질문 순번`이다. 이전 답변은 누적 보관한다. 질문 횟수의 고정 상한은 없지만, 한 번의 입력 크기는 제한하며 오래된 확인 내용은 AI 입력에서 제외될 수 있다. 제외 건수는 화면에 표시한다.
- Backend `POST /api/requirements/{requirementId}/follow-ups`는 완료된 분석이 현재 요구사항 버전과 같은 프로젝트에 속하는지, 사용자가 버전 편집 역할인지, 질문 번호가 원본 결과에 존재하는지 확인한다. Frontend 분석 결과 화면은 답변 저장 후 새 버전으로 재분석을 시작한다. 저장 성공·분석 시작 실패 시 동일 버전으로 재시도하도록 한다.
- **`supabase/migrations/009_requirement_follow_up.sql`은 2026-10-14 Supabase에 적용된 것을 읽기 전용 조회로 확인했다.** `parent_version_id` 컬럼·외래키가 존재하고, 당시 저장된 2개 버전에는 연결이 빠진 후속 버전이 없었다. Backend(8080)는 인증 없는 `/api/auth/me` 요청에 예상대로 401을 반환했고 AI 분석/추론 서버(8000)의 `/health`는 200이었다. 실제 계정으로 추가 질문 저장 → 새 버전 생성 → 재분석 → 이력 조회의 E2E 검증은 아직 하지 않았다.
- 2026-10-15 `b07cf79`에서 취소·실패한 후속 분석의 질문으로 돌아가 답을 수정할 수 있게 했다. 같은 답을 다시 제출하면 불필요한 새 버전을 만들지 않고 저장된 버전으로 분석을 재시도한다. `65cbe42`에서는 프론트가 저장된 답변을 복원하고 실패/취소 화면에서 원 질문으로 돌아가는 길을 표시한다. 별도 사용자 입력의 무제한 반복을 권장한다는 뜻은 아니다.
- 이 기능의 단위 테스트·빌드 통과는 권한별 UI, 긴 입력의 모델 품질, 모든 취소 경쟁 상태를 검증한 것은 아니다. AI 질문·답변과 분석 결과는 사람이 사실을 확인하기 전까지 승인된 정답이 아니다.

- 검토 상태 `APPROVED`는 누군가 버튼을 눌렀다는 기록이지 자동으로 사실 검증된 정답이라는 뜻이 아니다. 학습용으로는 요구사항·실제 전달 facts·AI 원본·수정본·검토 이유·프로젝트/버전 정보를 함께 점검한다.
- AI가 없는 파일/컬럼을 근거로 들거나 미결정 구현을 확정처럼 쓴 경우 원본 승인 대신 수정본 승인 또는 반려를 사용한다. 현재 화면의 비밀번호 초기화 사례는 이런 교정이 필요한 사례로, 원본을 학습 정답으로 사용하지 않는다.
- 더 묻지 않아도 영향 범위를 조건부로 설명할 수 있다면 확인 질문을 반복하지 않는다. 확정된 사실과 미결정 항목을 분리하고, 보류 조건이 남은 분석으로 저장할 수 있다. 학습 자체는 여러 프로젝트의 사람 승인 정답과 분리된 평가 세트가 쌓인 뒤에 진행한다.
