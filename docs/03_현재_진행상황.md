### 2026-10-21 AI 모델 관리의 실제 API 연결

### 2026-10-21 최신 재분석·승인·학습 전달 상태

이 절이 현재 상태다. 아래 절의 미완료·미반영 표시는 해당 작업 당시 기록으로 읽는다.

- AI 분석/추론 서버를 사용자 승인으로 재시작한 뒤 같은 요구사항을 재분석했다.
  작업 `42b126a7-33d6-417b-8815-ec815a519ba8`은 14:08:42경부터 14:17:03경까지 약 8분 21초에 완료했다.
  일반 분석·DB 다섯 묶음·종합은 검증된 저장 응답을 재사용하고 최종 정리만 새로 실행했다.
  위험도는 보통 43점, DB 판단은 추가 확인 필요다. 처음부터 전부 추론한 시간으로 비교하지 않는다.
- 담당자가 수정 결과를 승인했다. 수집 컬럼 13개·인덱스 4개에 맞춰 잘못된 인덱스 설명을 수정했고,
  실제 저장 대상·실행 경로·JSON 내부 값은 미확인으로 남겼다. JSON 키 부재를 전용 컬럼 추가의 필수 근거로 단정하지 않았다.
  원본 결과는 보존되며 이번 승인은 분석 검토이지 실제 DB 변경 승인이 아니다.
- 학습 초안의 일반 정답에는 일반 입력에 없는 컬럼·인덱스 상세 사실을 넣지 않도록 별도 수정했다.
  DB 정답에는 상세 구조를 유지했다. 현재 자동 초안은 최종 수정본을 일반 정답으로 복사할 수 있으므로,
  형식 검사를 통과해도 단계별 입력으로 답할 수 있는 내용인지 직접 검토해야 한다. 이 자동 분리 개선은 아직 하지 않았다.
  파일·줄 검사도 원본 입력을 기준으로 해 변환된 일반 입력에서 생략된 근거를 자동 차단하지 못하는 한계가 있다.
  합성 참조 81건 중 마지막 파일이 실제 메시지에서 빠져도 검사를 통과하는 것을 확인했으므로,
  맥북에서 학습 전 실제 메시지의 인용 근거 포함 여부를 확인한다. 이 자동 검증 개선은 별도 작업으로 남겼다.
- 사용자가 두 검토 확인란과 전체 검사를 마친 뒤 새 사례 한 건을 전송했다.
  게시 파일은 100,158바이트이며 NAS 사본·outbox·전송 기록의 크기와 SHA-256이 일치한다.
  전송 파일도 준비한 검토 초안과 두 확인 표시를 제외하면 동일하다. 실제 사례·가중치·비밀 설정은 Git에 넣지 않는다.
- 마지막 서버 조회에서는 새 파일의 `WAITING_FOR_FILE`, 기존 검증 사례 두 건을 확인했다.
  이후 사용자가 맥북 NAS 폴더의 파일 도착을 확인했다. 도착 확인과 수신 서버의 `VERIFIED`는 구분하며,
  맥북에서 새 사례까지 검증됐는지 확인한 뒤 학습 자료를 준비한다. 실제 업무 학습이나 운영 모델 전환은 아직 하지 않았다.

### 2026-10-20 DB 변경안의 중복·인덱스·필수 여부 보완

이전 검증에서 확인한 중복 컬럼 추가와 JSON `NOT NULL` 해석 오류를 보완했다.
새 변경 유형 `ADD_INDEX`와 항목별 `necessity`(`REQUIRED` 필수 변경 / `RECOMMENDED` 권장 개선)를 추가했다.
권장 개선만으로 `CHANGE_REQUIRED`를 확정할 수 없으며 같은 컬럼·테이블 추가의 중복을 거부한다.
인덱스 대상 컬럼은 관찰된 구조 또는 같은 계획의 새 컬럼 추가안과 대조한다.
프론트엔드는 유형과 필수·권장 구분을 표시하며 작성 안내에 새 JSON 위치를 추가했다.

동일한 중복·구분 규칙을 추론 응답, 백엔드 수신, 수정본 승인, 학습 수신 계약에 적용했다.
구형 `OTHER`나 없는 구분값은 조회 시 임의로 바꾸지 않으며 기존 승인·학습 파일을 수정하지 않는다.
잘못된 중복 원본은 계속 조회할 수 있지만 새로 원본 승인할 수는 없다.
새 추론은 모든 변경안에 구분을 요구하고, 저장 결과 재사용도 현재 검사를 다시 통과해야 한다.
프롬프트·응답 스키마가 달라 이전 DB 단계 결과는 그대로 재사용하지 않는다.

DB 지침은 SQL `NULL`, JSON 내부 `null`, 키 생략을 구분하고, 컬럼의 `NOT NULL`만으로 내부 키 제약을 단정하지 않도록 했다.
검색이 있다는 이유만으로 인덱스를 필수라고 하거나, 실행 계획·측정 없이 성능 우열을 단정하지 않도록 했다.
기존 구조 활용이 가능하면 새 컬럼을 유일한 필수 해법으로 제안하지 않고, 저장 방식이 미정이면 조건별 대안과 확인 질문을 남긴다.
이 지침에는 특정 프로젝트·테이블을 고정하지 않는다. 구조 검사는 문장 전체의 의미나 실제 성능을 증명하지 않으므로 담당자 검토는 유지한다.

수신 서버의 이전 검증기가 새 사례를 거부하지 않도록 게시 전 검증 기능 조회를 추가했다.

적용하고 수신 서비스를 재시작하기 전에는 새 사례를 전송하지 않는다. 게시 전 보호 장치가 파일 생성을 막는다.
로컬 검증 완료와 원격 수신 서버 업데이트 완료를 혼동하지 않는다.
최종 확인은 Backend 전체 테스트, 프론트엔드 린트·테스트 79개·빌드,
AI 분석/추론 서버 테스트 58개, 학습 도구 테스트 56개가 통과했다.
AI 테스트에는 임시 폴더와 로컬 HTTP를 사용하는 줄 단위·파일 단위 사례 전송 두 경로가 포함된다.
이 자동 검사에서 실제 업무 사례를 원격 학습 서버로 전송하거나 모델 학습을 시작하지 않았다.

AI 학습 서버의 수신 서비스에 `.env` 자동 로딩과 터미널 처리 로그를 추가했다.
실행 위치와 관계없이 `training/.env`를 읽고, 없으면 저장소 루트의 `.env`를 확인한다.
이미 설정한 환경변수가 우선하며 `--env-file`로 다른 파일을 지정할 수 있다.
수신에 필요한 공유 폴더 경로·전송 키만 읽고 셸 명령이나 환경변수 참조를 실행하지 않는다.
시작·기존 수신함 상태·알림 접수·파일 대기·도착·검증 완료·안전한 실패 코드를 터미널에 표시한다.
같은 파일의 같은 상태는 반복 출력하지 않으며 비밀키·서명·분석 원문·전체 파일 경로는 기록하지 않는다.
새 환경 설정·로그 동작은 자동 검사로 확인했으며 실제 MacBook의 재시작은 아직 수행하지 않았다.

MacBook에서 다음 순서로 이어간다.

1. 변경 커밋이 원격에 올라온 뒤 저장소 업데이트를 받는다. 기존 로컬 변경은 먼저 확인한다.
2. `training/.env`가 없다면 `training/.env.example`을 복사하고 해당 장비의 공유 폴더 절대 경로와 기존 전송 키를 넣는다. 비밀값은 Git에 올리지 않는다.
3. 기존 수신 서버 터미널에서 `Ctrl+C`로 종료한 뒤 저장소 루트에서 다음 명령을 실행한다. 추가 패키지 설치나 `source .env`는 필요 없다.

   ```bash
   training/.venv/bin/python training/receiver_service.py --host 0.0.0.0 --port 8011
   ```

4. 시작 로그의 `env_file=loaded`와 `validation_version=2`를 확인한다. 설정이 기존 환경변수에만 있다면 `not_found`여도 유효한 설정으로 시작할 수 있다.
5. 웹에서 현재 승인 사례를 다시 검사하고 전송한다. 터미널의 `VERIFIED`와 화면의 수신·검증 완료를 함께 확인한다. 이 상태는 학습 시작·완료가 아니다.

이번 수신 설정·로그 변경만 적용하려면 AI 학습 서버의 수신 서비스만 재시작한다.
현재 Mac Studio의 Backend와 AI 분석/추론 서버는 앞선 검증 변경으로 이미 재시작했다.

- `5afbd14` 학습 사례 식별자와 검토 확인 자동 반영: 프로젝트 그룹과 현재 로그인한
  검토자 ID를 서버에서 안정적인 비식별 식별자로 만들고 전송 시에도 서버 값으로 맞춘다.
  기존 분석 승인 시각과 사람이 수정한 정답은 보존하며, 화면 확인란은 승인·비식별화 값을
  JSON에 반영한다. 확인란을 선택하지 않으면 JSON을 직접 수정해도 전송을 승인하지 않는다.
- `9dcb96c` AI 분석·추론 서버와 학습 서버 명칭 통일: 화면·설정·오류·단계 내역·학습 도구에서

- 문서·구성도 묶음: 역할별 명칭, 확인한 두 장비 사양, 공유 NAS 역할의 iCloud Drive와
  모델 배포 방침을 갱신했다. 구현된 학습 사례 전달과 앞으로 구현할 모델 자동 배포를 구분한다.

이번 커밋 전 검증은 프론트엔드 린트·테스트 57개·운영 빌드, AI 분석/추론 서버 테스트
48개 통과·1개 건너뜀, 학습 도구 테스트 42개, 관련 백엔드 테스트 40개가 통과했다.
프론트엔드 빌드는 큰 번들 경고가 남아 있지만 성공했다. 실제 업무 사례 재전송이나
모델 학습·배포, 실행 중인 서버 재시작, 공유 DB 변경은 이번 검증에서 수행하지 않았다.

## 2. 실제 구현된 분석 흐름

```text
프로젝트 등록: 조직 선택/생성 → 프로젝트 저장 → Git·DB 연결 시험/저장
변경 분석: 프로젝트별 변경요청 테이블 검색 → 필요 시 등록 폼에서 Git 프로젝트 선택·요구사항/첫 버전 생성 → 현재 버전 ID 선택
공통: 요청 백엔드의 인스턴스 ID로 작업 PENDING 생성 → 지정된 Worker만 선점 RUNNING
  → 고정 Git commit 읽기 → 읽기 전용 DB 구조 → SQL/ORM 참조 → 입력 범위 검사
  → FastAPI → Qwen 전체 분석
  → 요구사항의 DB 관련성에 따라 DB 호출 생략 또는 추가 분석
  → 응답 재검증 → 결과·실제 전달 facts 저장 + COMPLETED
  → Frontend job별 polling 및 결과 조회 → 필요 시 추가 질문/새 버전 재분석
  → 권한 있는 사람이 AI 원본 승인·수정본 승인·반려 중 하나를 한 번 기록
```

Worker는 Backend 프로세스 안에서 실행한다. AI 분석/추론 서버는 Git/대상 DB에 직접 접속하지 않는다.
대상 DB의 업무 데이터 행을 모델로 보내거나 변경 SQL을 실행하지 않는다.
소스→DB 수집은 순차 처리이며 화면의 자동 상태 조회가 동시에 동작한다.
진행률 80%는 모델 대기 구간에도 나타나므로 시간 비율이나 남은 시간으로 해석하지 않는다.
화면은 서버 진행률을 임의로 높이지 않고 단계 활동·경과 시간으로 대기 중임을 보여준다. Backend Worker는 공개용 고정 문구의 단계 시작·완료 내역을 `analysis_jobs.analysis_options.activityLog`에 저장하고, 기존 작업 상태 API의 약 2.5초 조회로 최신 작업 내역을 보여준다. 최신 10건만 펼쳐 놓고 이전 내역은 접는다. AI 응답 대기가 길어지면 Backend가 30초마다 대기 중임을 기록하고 현재 단계 경과 시간은 매초 갱신한다. 이 기록은 **Backend가 응답을 기다린다는 뜻이지 모델 계산 완료율을 증명하지 않는다.** 원본 서버 로그·접속 정보·예외 내용은 화면에 전달하지 않는다. **모델 내부 토큰 진행률이나 남은 시간 예측은 아직 제공하지 않는다.**
AI 분석/추론 서버는 내부 키로 보호된 `/api/analysis/project/stream`에서 일반 영향 분석과 필요 시 DB 영향 분석의 시작·완료 및 응답 형식 재시도를 안전한 코드로 순차 전달한다. Backend가 이 코드를 사용자용 문구로 바꿔 같은 작업 내역에 저장한다. 구버전 AI 분석/추론 서버가 스트림 경로를 제공하지 않으면 기존 최종 JSON 경로로 대체하며, 이때 AI 내부 단계 내역은 나타나지 않는다. 단계 내역을 보려면 AI 분석/추론 서버·Backend가 모두 이 기능을 포함한 코드로 실행돼야 한다.
2026-10-14 로컬 재검증에서 AI 분석/추론 서버·Backend를 새 코드로 재시작했다. 실제 Qwen에 DB 저장 없는 최소 구조 분석을 스트림으로 요청하자 15·30·45·60초 heartbeat 후 약 66초에 `GENERAL_COMPLETED` → `DATABASE_SKIPPED` → 최종 결과가 도착했다. 최초 실행에서는 Python 3.9의 `asyncio.TimeoutError`를 처리하지 못해 15초에 연결이 끊겼으며, 이를 수정하고 회귀 테스트를 추가했다. AI 분석/추론 서버 테스트 44개가 통과했다. **당시 시험은 AI 스트림 경로만 검증했다.** 이후 2026-10-15 실제 완료 화면은 5절에 별도로 기록했다.
저장된 결과를 여는 `GET`은 모델을 다시 호출하지 않는다. 새 요구사항으로 분석을 시작할 때는 새 AI 판단이 필요하지만, 고정 Git SHA가 같고 현재 읽기 전용 DB 구조가 저장된 완전한 근거와 일치하면 Git 체크아웃·소스 재스캔을 생략한다. **DB 변경 여부 확인을 위한 구조 메타데이터 조회는 매번 수행**한다. 이전 소스/AI 입력/DB 수집이 잘렸거나 구조가 다르면 새로 수집하며, 재사용한 원본 작업 ID는 `analysis_jobs.analysis_options`에 남긴다.
요구사항 화면에서 **저장된 근거로 바로 분석**을 선택하면 완료된 작업의 소스·DB 근거를 기준으로 새 요구사항을 AI에 다시 분석시킨다. 이 방식은 사용자가 Git·DB에 변경이 없음을 확인해야 시작되며, **현재 Git·DB를 조회하지 않으므로 변경 여부를 자동 보증하지 않는다.** 후보는 수집 범위가 잘리지 않고 경고가 없는 완료 결과만 표시한다. 기본 선택인 **최신 Git·DB 확인**은 기존의 자동 비교 경로다.
분석 화면의 **이력으로 나가기**와 브라우저 뒤로가기·다른 화면 이동은 화면 조회만 중단하고 서버 작업은 유지한다. 진행 중에는 이동 확인을 보여준다. 새로고침·탭/창 닫기는 브라우저 기본 이탈 경고를 요청하지만 브라우저 설정에 따라 표시가 제한될 수 있으며, 종료 중 비동기 취소 요청은 보내지 않는다. **분석 작업 취소**는 `PENDING`/`RUNNING`을 `CANCELLED`로 변경하며 결과 저장을 막는다. 같은 Backend 인스턴스의 실행 스레드는 중단을 시도하지만, 여러 인스턴스나 원격 모델 계산이 즉시 멈춘다고 보장하지 않는다.
취소·실패한 후속 분석은 이전 완료 결과의 질문으로 돌아가 답을 수정하거나, 같은 답이라면 새 요구사항 버전을 늘리지 않고 재시도할 수 있다. 새 분석마다 위험 점수와 등급을 다시 산정하고, 불확실성이 해소돼도 변경 자체의 데이터·보안 위험을 자동으로 낮추지 않는다. 저장된 옛 결과의 점수·등급 불일치는 화면에서 점검 필요로 표시한다.
`PROJECT_SCAN_V2` 작업은 `target_worker_id`가 지정된 요청 백엔드만 선점하며, 선점한 `claimed_by_worker_id`를 남긴다. 다른 백엔드로 자동 인계하지 않는다. 적용·장애 처리·검증 기록은 [16번 문서](16_분석_워커_지정_운영.md)에 있다. 고착 작업을 실패 처리하는 로직이 있는 것과 lease/heartbeat·자동 재시도가 구현된 것은 다르다.
사람 검토에서는 AI 원본을 보존하고 승인/반려·검토자·시각·이유·선택적 수정 결과를 별도로 저장한다. 수정 JSON의 형식·크기·비밀정보 필드·위험 점수 일관성은 검사하지만 **파일/DB 근거의 사실 여부는 자동 보증하지 않으므로 승인자가 직접 확인**해야 한다. 한 번 저장한 검토 결정은 변경할 수 없다.

## 3. 현재 Backend API 범위

| 영역 | 구현 경로 |
|---|---|
| 사용자 | `GET /api/auth/me` |
| 조직 | `GET/POST /api/organizations`, `GET /api/organizations/{id}` |
| 조직 구성원 | 조직별 members 조회·추가·수정·삭제 |

| Git 연결 | repository-connection의 시험·저장·조회 |
| DB 연결 | database-connection의 시험·저장 |
| 요구사항 | 프로젝트별 requirements 생성·목록, 접근 가능한 프로젝트 통합 `GET /api/requirements`, 단건 `GET /api/requirements/{id}` |

현재 `/api/dashboard`, `/api/analyses`, `/api/models`, `/api/documents`, `/api/settings`에 대응하는 Controller는 없다. 분석 이력은 별도 `/api/analysis-jobs`에 구현했다.
아키텍처·영향도 전용 결과 API, 견적 API와 과거 요구사항 버전 목록 API는 아직 확인하지 못했다.
검토 API/화면이 생겼어도 학습 데이터 자동 추출·최종 견적 확정·고객 공개 기능까지 완성된 것은 아니다.
현재 `001`~`011` migration 파일이 있다. `009`의 적용은 이전 읽기 전용 조회로, `011`의 적용은 [16번 문서](16_분석_워커_지정_운영.md)의 실DB 검증으로 확인했다. `010`의 실제 DB 적용과 승인/반려 저장 경로는 MacBook에서 읽기 전용 스키마 확인 및 권한 있는 계정의 테스트로 다시 확인한다. 이 문서 갱신 과정에서 migration을 실행하지 않는다.

## 4. Frontend에서 먼저 보완할 부분

전체 화면별 판정과 파일 근거는 [13번 Frontend 점검](13_2026-10-14_Frontend_구현_점검.md)을 기준으로 한다.

1. **프로젝트 목록·상세·수정:** 소스 종류·브랜치 표시와 논리 삭제·복구, 상세 이동, 기본정보와 Git·DB 연결 계정 수정 화면을 연결했다. 실제 계정으로 연결 시험→저장→재조회 및 권한을 검증하고, 기술 스택 `stack`의 실제 근거 매핑과 Git 주소 변경·연결 저장의 원자화를 후속 처리한다.
2. **이력·실결과 경로:** 이력 목록·특정 job 재열기는 구현했다. 새 API의 실제 계정·브라우저 검증을 하고, 전역 아키텍처·영향도 데모를 실제 저장 결과로 연결한다.
3. **요구사항 버전·상태·검토·승인:** 추가 질문·새 버전 재분석과 결과 승인/반려 화면은 구현됐다. 우선 취소·실패 후 복원, 권한별 검토, 수정 JSON 검증을 실제 환경에서 시험한다. 과거 버전 조회·상태 변경 UI는 이후 범위다.
4. **오류·Mock 표시·미완성 버튼:** 없는 API·실행 미연결 버튼을 실제 기능처럼 표시하지 않고 빈 상태·실패·재시도·권한 거부를 처리한다.
5. **대시보드·조직·견적·고객 공개:** 각각 API/응답 정책과 UI를 기능 단위로 구현한다.
6. **모델·문서·설정 관리:** 운영 비밀의 서버 관리, 실제 학습/배포·업로드/RAG·권한을 갖춘 뒤 전환한다.
7. **검사·성능:** 최근 프론트 전체 lint·테스트·빌드 결과를 다시 확인하고, route lazy load와 실제 화면별 테스트는 이후 범위로 둔다.

학습 데이터 준비를 기다리는 동안에도 제품·Frontend 개발은 진행할 수 있다. 위 진행 화면 및 이력 재열기는 코드에 반영됐으므로 MacBook에서 중복 구현하지 말고 실제 연결을 검증한다.

## 5. AI와 MacBook 학습 상태

Mac Studio 기본 모델 선정과 운영 설정은 [10번](10_2026-10-14_AI_모델_선정_근거.md)·[11번](11_2026-10-14_MAC_STUDIO_QWEN_학습_평가_전달.md)을 참고한다.
대표 질문의 DB 단계는 팀/조직 확인을 요청했지만 전체 분석에는 근거가 약한 변경 제안이 남았다.
기존 기준 응답은 미승인 원본이며 학습 정답으로 바로 사용하지 않는다.
Mac Studio에서 요구사항 `REQ-001`의 Qwen 실제 전체 분석을 완료했다. 작업 `c48f6fdd-54db-4580-8455-b96efd4f0bdd`는 약 14분 22초의 AI 분석/추론 서버 요청 끝에 `COMPLETED`로 저장됐고, 테이블 26/26개·관계 81/81개가 모델 입력 범위에 포함됐다. 첫 DB 응답은 `DB_UNSUPPORTED_UNIQUE`로 거부됐으며 재시도 응답이 통과했다. 다만 일반 분석에는 기존 DTO와 DB 제약을 잘못 읽은 제안이 있어 **위험도 HIGH 85/100을 포함한 결과 전체가 사람 검토 전 상태**다. 사용자 확인으로 이 질문의 ‘팀’은 새 테이블이 아닌 **기존 `organization`**임이 확정됐다. 기존 프로젝트의 조직 미할당 행 처리와 ‘관리’ 권한 범위는 미확정이다. 다음 시험에는 이 해석을 요구사항 문구에 명시해야 한다.

이 성공은 **프롬프트 범용화·진행 화면 개선 이전**의 실행 결과다. 새 코드로 동일한 E2E를 완료했다고 기록하지 않는다. 이번 Mac Studio에서는 Git 임시 파일 소실 처리와 진단, 범용 프롬프트 및 JSON 응답 진단, 진행 화면 피드백을 커밋했다. 모델 교체·새 학습·승인 정답 생성은 하지 않았다.

MacBook의 Frontend·모의 API 검사는 Mac Studio 모델 없이 진행할 수 있다. 실제 Qwen E2E는 Backend가 Mac Studio FastAPI에 접근할 수 있고 양쪽의 내부 API 키가 일치해야 한다. 장비별 비밀값은 문서·커밋·화면 로그에 적지 않는다. 테스트 결과가 확인되기 전에는 견적·고객 공개·학습을 완료로 표시하지 않는다.

## 8. 추가 질문·답변 이어 분석

- 분석 결과의 `databaseImpact.openQuestions`에 사용자가 답하거나 자유 형식 질문을 추가하면, 이전 결과를 수정하지 않고 **같은 요구사항의 새 버전**을 만든다. 새 버전의 `parent_version_id` 외래키는 이전 버전을 직접 가리키며, 질문 식별자는 모델 문장이 아닌 `분석 작업 ID + 질문 순번`이다. 이전 답변은 누적 보관한다. 질문 횟수의 고정 상한은 없지만, 한 번의 입력 크기는 제한하며 오래된 확인 내용은 AI 입력에서 제외될 수 있다. 제외 건수는 화면에 표시한다.
- Backend `POST /api/requirements/{requirementId}/follow-ups`는 완료된 분석이 현재 요구사항 버전과 같은 프로젝트에 속하는지, 사용자가 버전 편집 역할인지, 질문 번호가 원본 결과에 존재하는지 확인한다. Frontend 분석 결과 화면은 답변 저장 후 새 버전으로 재분석을 시작한다. 저장 성공·분석 시작 실패 시 동일 버전으로 재시도하도록 한다.
- **`supabase/migrations/009_requirement_follow_up.sql`은 2026-10-14 Supabase에 적용된 것을 읽기 전용 조회로 확인했다.** `parent_version_id` 컬럼·외래키가 존재하고, 당시 저장된 2개 버전에는 연결이 빠진 후속 버전이 없었다. Backend(8080)는 인증 없는 `/api/auth/me` 요청에 예상대로 401을 반환했고 AI 분석/추론 서버(8000)의 `/health`는 200이었다. 실제 계정으로 추가 질문 저장 → 새 버전 생성 → 재분석 → 이력 조회의 E2E 검증은 아직 하지 않았다.
- 2026-10-15 `b07cf79`에서 취소·실패한 후속 분석의 질문으로 돌아가 답을 수정할 수 있게 했다. 같은 답을 다시 제출하면 불필요한 새 버전을 만들지 않고 저장된 버전으로 분석을 재시도한다. `65cbe42`에서는 프론트가 저장된 답변을 복원하고 실패/취소 화면에서 원 질문으로 돌아가는 길을 표시한다. 별도 사용자 입력의 무제한 반복을 권장한다는 뜻은 아니다.
- 이 기능의 단위 테스트·빌드 통과는 권한별 UI, 긴 입력의 모델 품질, 모든 취소 경쟁 상태를 검증한 것은 아니다. AI 질문·답변과 분석 결과는 사람이 사실을 확인하기 전까지 승인된 정답이 아니다.

### 사람 검토·학습에 넘길 때의 기준

- 검토 상태 `APPROVED`는 누군가 버튼을 눌렀다는 기록이지 자동으로 사실 검증된 정답이라는 뜻이 아니다. 학습용으로는 요구사항·실제 전달 facts·AI 원본·수정본·검토 이유·프로젝트/버전 정보를 함께 점검한다.
- AI가 없는 파일/컬럼을 근거로 들거나 미결정 구현을 확정처럼 쓴 경우 원본 승인 대신 수정본 승인 또는 반려를 사용한다. 현재 화면의 비밀번호 초기화 사례는 이런 교정이 필요한 사례로, 원본을 학습 정답으로 사용하지 않는다.
- 더 묻지 않아도 영향 범위를 조건부로 설명할 수 있다면 확인 질문을 반복하지 않는다. 확정된 사실과 미결정 항목을 분리하고, 보류 조건이 남은 분석으로 저장할 수 있다. 학습 자체는 여러 프로젝트의 사람 승인 정답과 분리된 평가 세트가 쌓인 뒤에 진행한다.
