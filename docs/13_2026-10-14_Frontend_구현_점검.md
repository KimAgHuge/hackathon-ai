# Frontend 구현·API 연결 점검

기준일: 2026-10-14 · 검토 기준: `adbd9c7` 소스 · 검토자: 김은태

**화면이 존재하는 것과 실제 기능이 완성된 것은 다르다.** 프로젝트 등록과 현재 요구사항 분석 경로는 연결돼 있지만,
프로젝트 상세·수정, 결과 전용 화면, 이력, 모델·문서·설정과 견적 업무는 남아 있다.
이번 작업은 코드·API 계약 점검과 문서 갱신이다. 아래 기능 결함을 수정했다고 해석하지 않는다.
로그인한 브라우저와 실제 Backend/Supabase를 연결한 E2E 시험은 수행하지 않았다.

## 확인된 계약 불일치·미동작

### 프로젝트 목록은 실제 API 전환만으로 완성되지 않는다

`ProjectManagementView.vue`는 `stack`, `source`, `branch`를 표시하지만
`ProjectResponse.java`에는 `sourceType`, `repositoryUrl`, `defaultBranch`가 있고 `stack`은 없다.
현재는 응답을 변환하지 않으므로 실제 목록의 소스·브랜치·기술 스택 표시가 맞지 않는다.
`openProject`·`editProject`는 `console.log`만 호출하고 상세 route·편집 화면이 없다.
`fetchProjects`에는 화면 오류 처리가 없다.

### 실제 Backend에 없는 화면 API

| Frontend 호출 | 실제 Backend 점검 결과 |
|---|---|
| `/api/dashboard` | 대응 Controller 없음 |
| `/api/analyses` | 대응 목록 API 없음. 단일 job·result API만 있음 |
| `/api/models`, `/api/documents` | 대응 Controller 없음 |
| `/api/settings` 및 AI/학습/Supabase 시험·저장 | 대응 Controller 없음 |
| `/api/projects/demo/architecture`, `/api/projects/demo/impact` | 대응 결과 API 없음 |
| `/api/projects/demo/analysis`, `/api/analysis-jobs/demo` | 기존 데모 래퍼. 실제 UUID 기반 분석 경로에 사용하지 않음 |

`VITE_USE_MOCK=false`는 Mock 대신 API를 호출하게 할 뿐 위 API를 만들지 않는다.
대시보드·이력·모델·문서 목록은 `finally`만 있어 API 실패를 사용자에게 안내하는 흐름도 부족하다.
Architecture/Impact store는 오류를 기록하지만 화면에서 이를 설명·복구하는 UI를 확인하지 못했다.

### 버튼·안내가 실제 기능을 보증하지 않는다

- AI 모델 `배포`는 console 출력만 하고, `학습 시작`·`배포 상태 확인`·`상세`는 실행 연결이 없다.
- `문서 업로드`는 클릭 핸들러나 파일 업로드 경로가 없다.
- 설정 Mock 응답은 실제 서버 설정을 바꾸지 않는다. 설정 화면의 내부 API 키·Supabase service-role 입력은 실제 운영 설정 방식과 별도로 재설계해야 한다. 서버 비밀값은 Backend 로컬 설정에서 관리한다.
- `StepHeader`의 “병렬 분석”·구조/영향도 단계는 목표/데모 표현이다. 실제 Worker는 Git→DB→관계→AI 순서이며, 데모 결과 화면으로 이어지는 완성된 실분석 wizard가 아니다.
- DDL 업로드, Tibero/MySQL/MariaDB/MSSQL, 공급자 App 연동은 현재 비활성·준비 중이다.

## 이미 구현된 기능을 다시 미구현으로 적지 않는다

실제 변경요청 화면은 `LiveRequirementAnalysis.vue`와 `requirementApi.js`를 사용한다.
현재 버전 생성·선택적 분석은 가능하고, Backend에는 별도 버전 생성·상태 변경 API도 존재한다.
다만 이 두 API의 Frontend 편집·상태 UI가 없다. 과거 버전 목록을 반환하는 API도 이번 Controller 점검에서 확인하지 못했다.
`AnalysisProgressView.vue`는 단순 한 번 조회가 아니라 polling·DB 판단·수집 근거·범위 경고를 표시한다.
기존 `/architecture`·`/impact` 데모와 실제 job 결과 화면은 서로 다른 경로다.

## 검증 결과

| 검사 | 이번 MacBook 결과 |
|---|---|
| `node --test tests/*.test.js` | 14개 통과: polling 11개·요구사항 payload 3개 |
| `npm run build` | 통과. JS 약 504.65 kB, gzip 151.52 kB, 500 kB chunk 경고 |
| `npm run lint` | 실패. Prettier 규칙 오류 113개, 미사용 router 변수 경고 1개 |
| 실제 인증·CRUD·모델 연결·브라우저 E2E | 이번 점검에서 미실행 |

현재 모든 route component를 정적 import한다. 화면별 lazy import·번들 분리가 후속 개선 후보다.
빌드·단위 테스트 통과는 UI 버튼·없는 API·모델 답변의 정확도를 검증하지 않는다.

## 다음 구현 순서와 완료 기준

1. **프로젝트 목록·상세·수정:** 실제 DTO 매핑, route·저장 동작, 오류·빈 상태·권한 처리.
2. **분석 이력·결과 재열기:** Backend 목록 API와 연결해 프로젝트·job·요구사항 버전을 복원한다.
3. **아키텍처·영향도 실결과:** demo 주소를 제거하고 특정 job의 저장 결과로 근거·DB 판단을 표시한다.
4. **요구사항 편집·검토·승인:** 버전·상태 API 연결, 과거 버전 조회 계약, 결과 수정·승인 API/화면을 만든다. 승인 데이터 확보와 직접 연결된다.
5. **대시보드·조직 관리:** 집계 계약과 구성원 관리 UI, 조직 간 접근 차단 E2E.
6. **견적·고객 공개:** 작업 항목·기간·비용·검토·공개 상태 API를 구현하고 고객 응답을 제한한다.
7. **모델·문서·설정 관리:** 실행 API·권한·업로드/인덱싱·배포 검증을 갖춘 뒤 실제 관리 기능으로 전환한다.
8. **표현·검사 정리:** Mock 표시와 준비 중 동작, lint 포맷, route lazy load, 화면별 테스트를 정리한다.

각 기능 완료는 실제 API 저장·재조회, 성공·빈 목록·오류·권한 거부, 다른 프로젝트/조직 선택,
새로고침 후 복원과 데모 자료 미혼입을 확인한 상태를 뜻한다.

근거: `frontend/src/router/index.js`, `src/views/*`, `src/api/*`, `src/stores/*`,
`backend/src/main/java/com/doenaai/*/controller/*`, `project/dto/ProjectResponse.java`.
