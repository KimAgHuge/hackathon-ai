## 사람 검토: 맞은 방향과 수정할 부분

- DB 분석은 ‘팀’이 기존 `public.organizations`인지, 새로운 엔티티인지 확정되지 않았음을 인정하고, 확정된 DB 변경안을 비워 둔 점이 적절하다. `public.projects.organization_id`가 단일 FK이므로 프로젝트 한 행은 최대 한 조직을 참조한다는 설명도 맞다.
- 일반 분석의 근거 문장은 `organization_id`가 nullable이라는 이유로 “프로젝트가 다중 조직과 연관될 수 있다”고 했다. nullable은 조직이 없을 수 있음을 뜻할 뿐, 한 행이 여러 조직을 참조한다는 근거가 아니다. 같은 결과의 DB 분석과도 모순된다.
- 일반 분석은 `ProjectCreateRequest`·`ProjectUpdateRequest`의 `organizationId` 필수화를 권했지만 두 DTO에는 이미 `@NotNull`이 있다. [생성 DTO](../../backend/src/main/java/com/doenaai/project/dto/ProjectCreateRequest.java), [수정 DTO](../../backend/src/main/java/com/doenaai/project/dto/ProjectUpdateRequest.java)를 기준으로 이 권고는 불필요하다.
- 일반 분석은 `project_members` 제거·통합과 접근 쿼리의 대폭 수정을 권했다. ‘팀’의 의미와 ‘관리’의 범위가 정해지지 않았으므로 확정 변경으로 제시하면 안 된다. 현재 [접근 조회](../../backend/src/main/java/com/doenaai/project/repository/ProjectAccessRepository.java)는 이미 `organization_members`를 조인해 활성 조직 멤버십을 확인한다.
- DB 조건별 경로에서 다른 테이블의 멤버십 일치를 `CHECK 제약이나 트리거`로 강제하라고 했다. 테이블 간 조회가 필요한 규칙을 단순 `CHECK`로 구현할 수 있다고 가정하면 안 된다. 구체적인 제약·트리거·서비스 검증 방식은 스키마와 권한 정책을 사람이 다시 설계해야 한다.
- 일부 일반 분석 근거는 `databaseSummary: projects table`을 파일처럼 표시하거나 수집된 소스 줄의 의미를 확장해 서술했다. 인용된 파일·라인이 실제 주장까지 뒷받침하는지 별도 확인이 필요하다.

따라서 이 응답의 위험 점수·권고안을 그대로 견적이나 마이그레이션 계획으로 사용하지 않는다. 사람 검토자가 요구사항의 ‘팀’ 의미, `project_members`의 역할, 조직 미할당 기존 행 처리 방침을 확인한 뒤 교정된 답변을 작성·승인해야 학습 후보가 된다.

### 사용자에게 확인한 업무 해석

2026-10-14 사용자 확인: 이 요구사항의 ‘한 팀’은 별도의 새 팀 엔티티가 아니라 **기존 `organization` 하나**를 뜻한다. 이는 업무 용어의 확정이지 위 AI 결과 전체의 승인은 아니다.

이 해석에서 `projects.organization_id`는 이미 한 프로젝트 행에 최대 한 조직을 연결한다. 신규 프로젝트 API도 조직을 필수로 받고 사용자의 활성 조직 소속을 확인하며, 일반 수정 API로는 프로젝트의 소유 조직을 바꿀 수 없다. 그러므로 이 요구사항만으로 새 팀 테이블, `organization_id`의 `UNIQUE` 제약, 기존 소유 컬럼 제거, `project_members` 삭제를 확정 제안하면 안 된다. 특히 `UNIQUE`는 ‘프로젝트당 조직 하나’가 아니라 ‘조직당 프로젝트 하나’라는 전혀 다른 제약을 만든다.

아직 확인되지 않은 것은 기존 프로젝트 중 `organization_id`가 비어 있는 행의 수와 처리 정책, 그리고 ‘관리’가 조직 구성원 전체를 뜻하는지 프로젝트별 OWNER/관리 권한을 뜻하는지다. 실제 행을 조회하거나 DB 변경을 적용하지 않았으므로, 최종 DB·권한 변경 필요 여부는 이 항목의 확인 후 결정한다. 현재 저장된 Qwen 결과는 그대로 미승인으로 둔다. 다음 분석을 실행한다면 요구사항 문구에도 ‘팀은 기존 소속 조직(`organization`)을 의미한다’를 넣어 모델이 같은 업무 해석을 입력으로 받게 해야 한다.

## 이번 검증에서 드러난 운영 문제

1. Git 스냅샷 다운로드 후 디스크 안전 검사에서 `DISK_SCAN_IO`가 간헐적으로 발생했다. JGit 임시 파일이 탐색 중 사라진 경우만 허용하고, 루트 소실·다른 I/O 오류·크기 제한은 계속 실패하게 하는 수정을 적용했다. 로컬 성공/제한 테스트를 추가했으며, 원격 재시험에서 수집이 통과했다. 더 많은 반복 시험으로 재발 여부를 확인해야 한다.
2. 300초 호출 제한은 실제 입력에 부족했다. 다만 600초로 늘린 뒤에도 두 단계+검증 재시도로 약 14분이 걸렸으므로, 단순 제한 확대가 성능 해결책은 아니다.
3. DB 응답은 이전 실행에서 삭제·제거 표현 때문에 두 차례 거부됐다. 이번에는 첫 DB 응답이 `UNIQUE` 표현 때문에 거부됐고 재시도 후 통과했다. 모델 지시를 보강했지만 안전 검증과 표현 충돌의 재현 가능성을 더 시험해야 한다.
4. 현재 진행률 80%는 AI 내부의 일반/DB/재시도 단계를 구분하지 않는다. 단계별 시간·토큰·검증 실패 코드를 비밀정보 없이 수집하고 UI에서 진행 상황을 구분할 필요가 있다.
